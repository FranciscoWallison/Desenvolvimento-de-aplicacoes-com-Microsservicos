## 💉 SQL Injection — o teste da aspa simples

> **Teste de fumaça clássico:** colocar uma **aspa simples (`'`)** num campo. Se a aplicação retornar **erro de sintaxe SQL**, ela está **concatenando** a entrada direto na query — vulnerável a SQL Injection.

### Por que a aspa quebra a query

Se o login monta a SQL por **concatenação**:

```java
// ❌ VULNERÁVEL
String sql = "SELECT * FROM usuarios WHERE email='" + email + "' AND senha='" + senha + "'";
```

Com `senha = '` (aspa simples), a string vira:

```sql
SELECT * FROM usuarios WHERE email='alura@alura.com.br' AND senha='''
                                                                    ↑ aspa sobrando → erro de sintaxe
```

A aspa **fecha** a string antes da hora e desbalanceia a query → **Exception de sintaxe SQL**. Isso **prova** que a entrada é interpretada como **código**, não como **dado** — o mesmo mecanismo do `' OR 1=1 --` ([88.md](88.md)).

### A correção — PreparedStatement (query parametrizada)

```java
// ✅ SEGURO
String sql = "SELECT * FROM usuarios WHERE email=? AND senha=?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, email);
ps.setString(2, senha);
```

Com **`PreparedStatement`** e **placeholders (`?`)**, o driver envia a **query** e os **dados** separadamente — o valor **nunca** é interpretado como SQL. A aspa simples passa a ser só um caractere comum. (Em JPA/Hibernate, o equivalente é **parâmetros nomeados/posicionais**, nunca concatenar em JPQL/HQL.)

## 📝 Quiz Oficial do Curso — Aspa simples gera Exception SQL

> **Cenário:** no login, você põe email válido e **`'`** (aspa simples) na senha. Volta uma **Exception de erro de sintaxe SQL**. O que isso significa?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | Comportamento **esperado**; a aspa gera erro e a Exception "avisa o usuário" — nada a mudar | ❌ |
| B | O usuário só não digitou caracteres suficientes na senha — basta pôr mais de um | ❌ |
| **C** | Falta **validação/tratamento** da entrada; o usuário pode **injetar SQL** e obter dados do sistema — é uma **vulnerabilidade** a corrigir | ✅ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: C.** A Exception é um **sintoma**: a aplicação **concatena** a entrada na query, então a aspa é interpretada como **SQL**. Se uma aspa quebra a sintaxe, um payload bem construído (`' OR 1=1 --`, `' UNION SELECT ...`) **executa** comandos — é **SQL Injection** ([OWASP A03](47.md)). Precisa ser corrigido com **PreparedStatement/queries parametrizadas** (+ validação de entrada).

**Por que as outras estão erradas:**
- **A** — **perigosíssima:** tratar isso como "normal" ignora a falha. Pior ainda, deixar a **Exception de SQL vazar** para o usuário é **Information Disclosure** ([89.md](89.md)) — mostra ao atacante que há SQLi e detalhes do banco.
- **B** — nada a ver com "quantidade de caracteres". O erro é de **sintaxe SQL** causado pela aspa, não uma regra de tamanho de senha. Confunde o sintoma.

> 🔑 **A aspa que quebra é um presente para o atacante:** ela confirma a injeção. Corrija a **causa** (parametrização), não o sintoma.

</details>

## 🤖 Prática — SQLi automatizado com sqlmap (do Kali)

> Depois do bypass manual, automatizamos a exploração com o **sqlmap** — que detecta e explora SQLi sozinho, e **extrai** dados do banco.

**Passos:**
1. Logar no Kali (lab): usuário `root`, senha `toor`.
2. Descobrir o **IP do host** onde roda o Tomcat (`ipconfig` no Windows / `ifconfig` no Linux/Mac).
3. No Kali, acessar `http://[IP-do-host]:8080/alura-shows`, **logar** com Alex (`alex@gmail.com` / `123`) e **copiar a URL** pós-login (que traz parâmetros).
4. Rodar o sqlmap apontando para essa URL:

```bash
sqlmap -u "[URL copiada após o login]" --dump -T usuario -D owasp
```

| Trecho | Significado |
|--------|-------------|
| `-u "..."` | URL alvo (com o parâmetro vulnerável) |
| `--dump` | **Extrai** (despeja) o conteúdo |
| `-T usuario` | Tabela alvo |
| `-D owasp` | Banco (database) alvo |

**Resultado:** o sqlmap confirma a SQLi e **despeja a tabela `usuario` inteira** — dados de **Alex e Fernando** (emails, hashes de senha…). 💥

> 🔑 **Por que isso assusta:** o bypass manual dava **acesso a uma conta**; o sqlmap **automatiza** a extração de **todo o banco** — e testa dezenas de técnicas (union-based, blind, time-based) sem esforço. Uma app vulnerável a SQLi está exposta a **vazamento total**, não só a um login burlado.

> ⚠️ **Ética (o próprio curso reforça):** **nunca** use o sqlmap contra sistemas de terceiros. Só no seu lab autorizado.

> ✅ **A correção é a mesma:** **PreparedStatement/queries parametrizadas** (+ hash forte, menor privilégio no usuário do banco). Com parametrização, o sqlmap **não acha** parâmetro injetável. *(o curso corrige isso na próxima aula.)*

> ```bash

> ```
> Executado com sucesso, o que se espera?

| D | Todas as entradas da tabela `owasp` no banco `usuario` | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: B.** As flags dizem exatamente isso: **`-D owasp`** (database) + **`-T usuario`** (table) + **`--dump`** (extrair **todo** o conteúdo). Com a app vulnerável, o sqlmap despeja **todas as linhas** da tabela `usuario`.

**Por que as outras estão erradas:**
- **A** — `--dump` **é** um parâmetro válido e central do sqlmap (é justamente o que extrai os dados).
- **C** — `--dump` traz a tabela **inteira**, não só a 1ª linha (para limitar, usaria-se algo como `--start`/`--stop`).

## 🚫 Prática — GET → POST **não** corrige SQLi

> Tentativa comum (e **errada**) de "esconder" a falha: mover os parâmetros da **URL** (GET) para o **corpo** (POST). Vamos ver que **não adianta**.

**Mudanças feitas:**
- Na **JSP** (`usuario`), trocar o `method` do form de **GET** para **POST**.
- No **`UsuarioController`**, aceitar o `/login` só via **POST**.
- Efeito visível: email/senha **somem da URL** (vão no corpo). ✅ *isso é bom* — mas **não** resolve a SQLi.

**Novo teste com sqlmap** (agora com `--data` para o corpo POST):

```bash
# limpar cache de testes anteriores do sqlmap
rm -r /root/.sqlmap/output/

sqlmap -u "[url após login POST]" --dump -T usuario -D owasp --data="email=alex@gmail.com&senha=123"
```

| Flag | Significado |
|------|-------------|
| `--data="..."` | Envia os parâmetros no **corpo** (força método **POST**) |

**Resultado:** o sqlmap **ainda despeja** a tabela `usuario`. 💥 GET→POST **não** protegeu nada.

### Por que não resolveu

> 🔑 **A causa da SQLi é a concatenação, não o método HTTP.** O problema está no **`UsuarioDaoImpl`**, que **concatena** os parâmetros do formulário direto na query. **De onde** o parâmetro vem (URL/GET ou corpo/POST) é **irrelevante** — se ele é concatenado, é injetável. O sqlmap testa os dois com a mesma facilidade (`--data` para POST).

| Mito | Realidade |
|------|-----------|
| "Tirar da URL (POST) esconde/corrige a SQLi" | ❌ POST só muda **onde** o dado viaja; a injeção continua |
| "GET é inseguro, POST é seguro" | ❌ Ambos são iguais para SQLi; POST é melhor **só** para não expor dados na URL/logs ([89.md](89.md)) |
| A correção real | ✅ **PreparedStatement** no DAO — tratar o parâmetro como **dado**, nunca concatenar |

> 💡 **Lição que generaliza:** mudar a **superfície** (método, ofuscação, esconder) não corrige uma vulnerabilidade de **código**. Só a **correção na raiz** (parametrização) elimina a SQLi. *(o curso corrige o `UsuarioDaoImpl` na próxima etapa.)*

**Por que as outras estão erradas:**

## ✅ A correção — PreparedStatement (e JPA)

> **Para saber mais.** No curso a SQLi foi corrigida com a especificação **JPA** (parâmetros do ORM). Uma alternativa em **JDBC puro** é o **`PreparedStatement`** — a ideia é a mesma: **isolar a query dos parâmetros**.

```java
String sql = "insert into USUARIO (email, senha, nome, nomeImagem) values (?,?,?,?)";
PreparedStatement stmt = connection.prepareStatement(sql);

stmt.setString(1, usuario.getEmail());
stmt.setString(2, usuario.getSenha());
stmt.setString(3, usuario.getNome());
stmt.setString(4, usuario.getNomeImagem());   // (na apostila aparece "3" por erro de digitação — o correto é 4)
```

### Como isso mata a SQLi

| Etapa | O que acontece |
|-------|----------------|
| **`?` (placeholder)** | A query é enviada ao banco **com a estrutura já fixa** — "ainda não sei o valor, mas ele vai **aqui**" |
| **`setString(i, valor)`** | O driver envia o **valor separadamente**, ligado à posição `i` |
| **Resultado** | O banco trata o valor **sempre como dado**, **nunca** como SQL — `' or 'a'='a` vira só uma string literal |

> 🔑 **A diferença de mentalidade:** na concatenação, **query + dado viram uma string só** (o banco não distingue) → injeção. No PreparedStatement, **query e dado trafegam separados** → o dado **nunca** é interpretado como comando. É a **correção na raiz** que faltava em todas as práticas anteriores (aspa, bypass, sqlmap GET/POST).

> 💡 **Equivalência:** **JPA/Hibernate** (`setParameter`, parâmetros nomeados `:email`) e **PreparedStatement** (JDBC, `?` + `setString`) resolvem **o mesmo problema** do mesmo jeito — parametrização. Escolha a camada que seu projeto usa; **nunca** concatene.

> 📌 **Detalhe (fidelidade):** no material, a 4ª linha usa `setString(3, ...)` — é um **typo**; o índice correto é **`4`** (4º `?`). Índices do PreparedStatement começam em **1** e são **sequenciais**.

### 🛠️ A correção aplicada no curso — JPA / `EntityManager`

O curso corrigiu o `UsuarioDaoImpl` (que **concatenava**) usando a **JPA** via `EntityManager`:

**1. Injetar o EntityManager** (em vez de `ConnectionFactory` + SQL na mão):
```java
@PersistenceContext
private EntityManager manager;
```

**2. Persistir com `persist`** (sem montar INSERT):
```java
public void salva(Usuario usuario) {
    manager.persist(usuario);
}
```

**3. Consultar com parâmetros nomeados** (a parte crítica contra SQLi):
```java
public Usuario procuraUsuario(Usuario usuario) {
    TypedQuery<Usuario> query = manager.createQuery(
        "select u from Usuario u where u.email=:email and u.senha=:senha", Usuario.class);
    query.setParameter("email", usuario.getEmail());
    query.setParameter("senha", usuario.getSenha());
    return query.getResultList().stream().findFirst().orElse(null);
}
```

> 🔑 **O que muda:** os `:email` / `:senha` são **parâmetros nomeados** — o valor entra via `setParameter`, **separado** da query (JPQL). É a mesma ideia do `?` do PreparedStatement, na camada do ORM. O input **nunca** vira comando.

### ✅ Validação final — sqlmap não acha injeção

Depois da correção, limpar o cache e repetir o teste:
```bash
rm -r /root/.sqlmap/output/
sqlmap -u "[URL]" --dump -T usuario -D owasp --data="email=alex@gmail.com&senha=123"
```

**Resultado:** o sqlmap reporta que os **parâmetros não são injetáveis** — a SQLi foi **eliminada na raiz**. 🎉

> 🧩 **O arco completo de SQLi (neste doc):**
> **detectar** (aspa → Exception) → **explorar** (bypass `x' or 'a'='a`, sqlmap `--dump`) → **descartar falsa correção** (GET→POST **não** resolve) → **corrigir de verdade** (JPA `setParameter` / PreparedStatement `?`) → **validar** (sqlmap: não injetável). Só a **parametrização** fechou a porta.

Não é "executa e depois pega"; é "estrutura e dados trafegam separados". Mesmo com a frase imprecisa, **B é a única correta** (é a única que identifica a prevenção de SQLi).

</details>

## 🔬 Prática — bypass de login na Alura Shows

> O projeto do curso é a **Alura Shows** (Java + **Tomcat** + **MySQL**, deliberadamente vulnerável para corrigirmos). Aqui exploramos o **login bypass** por SQLi.

### Setup

1. Rodar o **Tomcat** com a Alura Shows → cria o banco `owasp` e as tabelas no MySQL.
2. Inserir os perfis (roles):
   ```sql
   use owasp;
   insert into Role(name) values ("ROLE_USER");
   insert into Role(name) values ("ROLE_ADMIN");
   ```
3. Acessar `localhost:8080/alura-shows` e cadastrar 2 usuários (Alex / Fernando).

### O ataque — autenticar como Fernando **sem saber a senha**

No campo **senha** do login do Fernando:

```sql
x' or 'a'='a
```

**Resultado:** login **efetuado como Fernando** — sem conhecer a senha real. 💥

### Por que funciona

A query concatenada monta algo como:

```sql
SELECT * FROM Usuario WHERE email='fernando@gmail.com' AND senha='x' or 'a'='a'
```

- `senha='x'` → **falso** (a senha não é `x`)
- `or 'a'='a'` → **sempre verdadeiro**
- Pela precedência, o `OR` faz a condição inteira retornar **verdadeira** → a query devolve o usuário e a app **autentica**.

> 🔑 É a **mesma família** do `' OR 1=1` ([88.md](88.md)): injetar uma condição **sempre verdadeira** para burlar a lógica. Aqui o impacto é **Spoofing/Elevation** ([STRIDE](89.md)) — assumir a identidade de outro usuário.

### A correção (mesma do teste da aspa)

**PreparedStatement** com placeholders — o `x' or 'a'='a` passa a ser tratado como uma **senha literal** (que simplesmente não confere), nunca como SQL:

```java
String sql = "SELECT * FROM Usuario WHERE email=? AND senha=?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, email);
ps.setString(2, senha);   // "x' or 'a'='a" vira apenas texto — login falha, como deveria
```

> 💡 **Camadas extras** (defesa em profundidade): a senha nem deveria ser comparada **em texto na query** — o certo é buscar o usuário pelo e-mail e conferir o **hash** ([bcrypt/Argon2, 89.md](89.md)) na aplicação. Assim, mesmo sem SQLi, não se compara senha crua no SQL.

### 📝 Quiz Oficial do Curso — A autenticação será realizada?

> **Cenário (entrevista):** cenário vulnerável, a query executada é:
> ```sql
> select * from usuario where email='alura@alura.com.br' and senha='x' or a=a'
> ```
> Sabendo que **nenhum usuário** tem essa "senha", qual o resultado?

| | Alternativa | Veredito |
|--|-------------|----------|
| **A** | Exception de **erro de sintaxe SQL** | ✅ |
| B | "Usuário não encontrado" (ninguém tem essa senha) | ❌ |
| C | Exception de "senha não reconhecida" | ❌ |
| D | O atacante **se autentica** como `alura@alura.com.br` | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: A — erro de sintaxe.** ⚠️ **Atenção à contagem de aspas** (é a pegadinha). Esta injeção é `x' or a=a` (com `a=a` **sem aspas**), então a query fica:

```sql
select * from usuario where email='alura@alura.com.br' and senha='x' or a=a'
```

Na parte da senha, `'x' or a=a'` tem **3 aspas** (ímpar → **desbalanceado**):
- `'x'` → string fechada
- ` or a=a`
- `'` → **abre uma aspa que nunca fecha** → *unterminated string* → **erro de sintaxe SQL** → **não autentica**.

**Contraste com a [prática acima](#-prática--bypass-de-login-na-alura-shows)** (que **funciona**): lá a injeção é `x' or 'a'='a` (com `'a'='a'` **entre aspas**), gerando `'x' or 'a'='a'` — **4 aspas, balanceado**: `'x'`, ` or `, `'a'='a'`. Aí sim monta um `OR` verdadeiro e autentica.

> 🔑 **A diferença é uma aspa.** `x' or a=a` (ímpar → erro) × `x' or 'a'='a` (par → bypass). O atacante precisa **balancear as aspas** para a injeção ser SQL válido — senão só derruba a query com Exception.

**Por que as outras estão erradas:**
- **B / C** — não é "usuário não encontrado" nem "senha não reconhecida": a query **nem chega a executar** — quebra na **sintaxe** antes de comparar qualquer coisa.
- **D** — seria o resultado se as aspas estivessem **balanceadas** (`x' or 'a'='a`). Com `x' or a=a`, a aspa sobrando causa **erro**, não login.

> 📝 **Nota (revisão):** eu havia marcado **D** inicialmente por semelhança com a injeção da aula anterior — mas o payload aqui é **diferente** (`a=a` sem aspas) e **desbalanceia** a query. O correto é **A**.

</details>

## 🔒 Hashing de senha com BCrypt

> **Novo tema (2ª vulnerabilidade do curso):** a Alura Shows salvava a senha **em texto claro** — qualquer um com acesso ao banco lê a senha de todos. A correção: **hash com BCrypt** (a mitigação que o [89.md](89.md) e o teste da aspa/[88.md](88.md) apontavam: *MD5 → bcrypt/Argon2*).

### O código (no `salva` do `UsuarioDaoImpl`)

```java
public void salva(Usuario usuario) {
    transformaASenhaDoUsuarioEmHash(usuario);
    manager.persist(usuario);
}

private void transformaASenhaDoUsuarioEmHash(Usuario usuario) {
    String salto = BCrypt.gensalt();                          // 1. gera um salt aleatório
    String senhaHashed = BCrypt.hashpw(usuario.getSenha(), salto);  // 2. hash(senha + salt)
    usuario.setSenha(senhaHashed);                            // 3. guarda o HASH, não a senha
}
```

### O que cada passo faz

| Passo | Método | Papel |
|-------|--------|-------|
| 1 | `BCrypt.gensalt()` | Gera um **salt** (valor aleatório) único por senha |
| 2 | `BCrypt.hashpw(senha, salto)` | Produz o **hash** da senha **+ salt** |
| 3 | `usuario.setSenha(senhaHashed)` | Persiste o **hash** no banco (a senha original **nunca** é salva) |

**Validação:** ao cadastrar a Ana (`789`) e rodar `select * from Usuario`, a coluna senha mostra um **hash BCrypt** (`$2a$10$...`), não `789`. ✅

### Por que salt + BCrypt (não MD5)

| Conceito | Por quê |
|----------|---------|
| **Salt** | Valor **aleatório** somado à senha → duas pessoas com a **mesma senha** geram **hashes diferentes**; **quebra rainbow tables** |
| **BCrypt é lento (work factor)** | Propositalmente **caro** de calcular → brute-force fica **inviável** (≠ MD5, rápido demais) |
| **Hash é unidirecional** | Não dá para "descriptografar" — no login, faz-se `BCrypt.checkpw(senhaDigitada, hashSalvo)` |

> 🔑 **Como fica o login:** você **não** compara senha com senha. Guarda o **hash**; na autenticação, o BCrypt **reprocessa** a senha digitada (o salt já vem embutido no próprio hash) e compara os hashes com `checkpw`. Assim, nem o time nem um atacante com o banco veem a senha real.

> 🧩 **Fecha o gancho:** no [89.md](89.md) (DREAD), o *Damage* de um vazamento do BD foi **8, não 10, "se as senhas estiverem bem cifradas"**. **Isto** é "bem cifrada": **BCrypt + salt** — não texto claro, não MD5.

> **Cenário:** usamos `BCrypt.gensalt()` para gerar um salt. O que é o salt?

|--|-------------|----------|

| B | O **valor digitado** pelo usuário no formulário, que será persistido | ❌ |
| C | O **resultado final** da codificação da senha, que é armazenado | ❌ |
| **D** | Um **valor aleatório** adicionado à senha para gerar o **hash** | ✅ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: D.** O **salt** é um **valor aleatório** (gerado por `gensalt()`) combinado com a senha **antes** de calcular o hash. Serve para que **senhas iguais** gerem **hashes diferentes** — anulando **rainbow tables** e ataques em lote.

**Por que as outras estão erradas:**
- **A** — salt **não tem relação** com chave primária; um é dado de segurança de senha, o outro é identificador de linha no BD.
- **B** — o valor digitado é a **senha**, não o salt. O salt é gerado pelo **sistema** (aleatório), não vem do formulário.
- **C** — o "resultado final da codificação" é o **hash** (o que `hashpw` retorna), não o salt. O salt é **entrada** do processo, o hash é a **saída**.

> 🔑 **Distinguir os três:** **senha** (entrada do usuário) + **salt** (aleatório do sistema) → `hashpw` → **hash** (o que se guarda). O salt costuma ficar **embutido no próprio hash** do BCrypt, para permitir a verificação depois.

</details>

### 🔓 O outro lado — login com `BCrypt.checkpw`

> Guardamos o **hash** (não a senha). Então o login **não pode** mais comparar senha na query — quem compara é o **BCrypt**.

**1. Tirar a senha da query** (buscar só pelo e-mail):
```java
TypedQuery<Usuario> query = manager.createQuery(
    "select u from Usuario u where u.email=:email", Usuario.class);
query.setParameter("email", usuario.getEmail());
// (removido o setParameter("senha", ...))
```

**2. Validar a senha com o hash do banco:**
```java
private boolean validaASenhaDoUsuarioComOHashDoBanco(Usuario usuario, Usuario usuarioRetornado) {
    if (usuarioRetornado == null) {
        return false;   // e-mail não existe
    }
    return BCrypt.checkpw(usuario.getSenha(), usuarioRetornado.getSenha());
    //                    ↑ senha digitada        ↑ hash salvo no banco
}
```

**3. Decidir o login no `procuraUsuario`:**
```java
if (validaASenhaDoUsuarioComOHashDoBanco(usuario, usuarioRetornado)) {
    return usuarioRetornado;   // senhas compatíveis → autentica
}
return null;                   // incompatíveis → falha
```

**Resultado:** logar com a Ana (`789`) funciona — o `checkpw` **reprocessa** `789` com o salt embutido no hash e confere. ✅

### Por que a query mudou (busca só por e-mail)

| Antes (senha em texto) | Depois (hash) |
|------------------------|---------------|
| `where email=:email and senha=:senha` | `where email=:email` |
| Comparava a **senha crua** no SQL | Compara o **hash** na aplicação (`checkpw`) |
| Impossível com hash | O hash salvo **≠** senha digitada — só o BCrypt sabe conferir |

> 🔑 **Por que não dá para comparar hash na query?** Cada cadastro gera um **salt diferente**, então o **mesmo `789`** vira um **hash diferente** a cada vez. Não dá para "`where senha = hash(789)`" — você **não** sabe qual salt usar. Por isso: **busca pelo identificador (e-mail)** → pega o hash salvo → **`checkpw`** reprocessa a senha digitada com o salt embutido e compara. Este é o **padrão** de login com hash salgado.

> 🧩 **Ciclo de senha completo (neste doc):** cadastro → **`gensalt` + `hashpw`** guarda o hash; login → busca por e-mail → **`checkpw`** valida. Nunca se guarda nem se compara a senha em claro.

## 🥊 Prática — brute-force de login com Burp Suite (Intruder)

> **Nova ameaça:** hashing protege o **banco** (se vazar), mas **não** impede um atacante de **adivinhar a senha pelo próprio formulário de login**. Aqui usamos o **Burp Suite** para automatizar esse brute-force.

### O que é o Burp Suite

> **Burp Suite** é uma plataforma de teste de segurança web que funciona como **proxy interceptador**: o tráfego do navegador passa por ele, permitindo **ver, modificar e reenviar** requisições. O módulo **Intruder** automatiza o envio de **muitas** requisições variando um campo (ideal para brute-force/fuzzing).

### Os passos (do Kali)

1. **Escopo:** `Target → Scope → Add` a URL da Alura Shows.
2. **Configurar o proxy do navegador** para `127.0.0.1:8080` (Preferences → Network → Settings) → o tráfego passa a atravessar o Burp.
3. **Interceptar** (`Proxy → Intercept is on`) e fazer login com `ana@gmail.com` + senha qualquer (`12345`).
4. **Enviar ao Intruder** (botão direito na requisição → *Send to Intruder*).
5. Em **Positions**: `Clear` tudo, selecionar o valor da **senha** e `Add` (marca **só** a senha como variável).
6. Em **Payloads**: inserir ~10 senhas candidatas, incluindo a correta (`789`).
7. **Start Attack**.

**Resultado:** só a senha **correta (`789`)** retorna **HTTP 200 (OK)**; as erradas dão **302** (redirect de volta ao login). O status **denuncia** qual senha funcionou. 💥

> ⚠️ **Lembrete do curso:** com o proxy ativo, ao fechar o Burp você **perde internet** no navegador. Depois do exercício: Preferences → Network → Settings → **No proxy**.

### A lição de defesa (conecta com o [89.md](89.md))

> 🔑 **Hash não impede brute-force pelo login.** O BCrypt garante que um vazamento do banco não entregue senhas — mas o **formulário de login** continua um oráculo: tentar → ver 200/302. Um atacante testa milhares de senhas automaticamente (Burp Intruder, Hydra…).

Mitigações (as **mesmas** do [89.md](89.md), agora com o atacante concreto na frente):

| Defesa | Como atrapalha o Intruder |
|--------|---------------------------|
| **Rate limiting + backoff** | Reduz drasticamente as tentativas/seg |
| **CAPTCHA** após N falhas | Quebra a automação |
| **MFA (2º fator)** | Acertar a senha **não basta** |
| **BCrypt (work factor alto)** | Cada tentativa fica **cara** — brute-force online lento |
| **Não vazar 200×302 tão claramente** | Resposta/tempo uniformes dificultam distinguir acerto |
| **Alertar no SIEM** | Pico de 401/302 do mesmo IP → detecção ([74.md](74.md)) |

> ⚖️ **Cuidado (do [89.md](89.md)):** a mitigação de brute-force **não** deve ser **lockout de conta** — vira DoS. Prefira rate limit + CAPTCHA + MFA.

> 🧭 **Ética:** Burp/Intruder só no **lab autorizado** (Alura Shows). Brute-force em sistemas de terceiros é crime.

## 🤖 Defesa — Google reCAPTCHA no login (parte 1: front)

> **A defesa contra o brute-force do Burp:** o **reCAPTCHA** valida que quem envia o login é **humano**, não um script. É a mitigação "CAPTCHA após N falhas" da tabela acima, aplicada na prática.

### Configuração (client-side)

1. Ter conta Google → acessar **google.com/recaptcha** → **Get reCAPTCHA**.
2. Registrar um site: label `alura-shows`, informar os **IPs/domínios** aceitos (incluir `127.0.0.1` **e** o IP do Tomcat, para o Kali alcançar) → aceitar termos → **Register**.
3. O Google gera **duas chaves**: **site key** (pública, vai no front) e **secret key** (privada, fica no servidor).
4. Colar a **tag `<script>`** do reCAPTCHA no rodapé (JSP `rodapé`).
5. Colar a **`<div class="g-recaptcha" data-sitekey="...">`** no formulário de login (após a senha).

**Resultado:** o **widget "Não sou um robô"** aparece no login. ✅

> ⚠️ **Só o front NÃO valida nada ainda.** O botão aparece, mas a checagem real é **no servidor**: a app precisa **enviar ao Google** o token gerado + a **secret key** para o Google confirmar se foi humano. Isso é a **parte 2** (server-side, próxima aula).

### Site key × secret key (não confundir)

| Chave | Onde fica | Papel |
|-------|-----------|-------|
| **Site key** | No **HTML/front** (pública) | Renderiza o widget |
| **Secret key** | No **servidor** (segredo!) | Valida o token junto ao Google — **nunca** exposta no front |

> 🔑 **Por que isso derrota o Intruder:** o Burp Intruder dispara requisições **direto**, sem resolver o desafio do reCAPTCHA. Sem um token válido, o servidor (na parte 2) **rejeita** o login — a automação de brute-force **quebra**. É a aplicação concreta do "CAPTCHA" do [89.md](89.md).

> 💡 **Camadas, não bala de prata:** reCAPTCHA atrapalha **bots**, mas não substitui **rate limiting**, **MFA** e **hash forte**. Defesa em profundidade — cada camada cobre o que a outra deixa passar.

- **B** — `127.0.0.1` é **reservado e fixo** (bloco `127.0.0.0/8`), **não** vem de DHCP nem muda. IPs de DHCP são da LAN (ex.: `192.168.x.x`).

## 🔗 reCAPTCHA parte 2 — validação server-side com Retrofit

> Agora a **parte 2** (a que realmente valida): o servidor envia o **token do clique** + a **secret key** ao Google (`siteverify`) e recebe se foi **humano**. Usamos o **Retrofit** (cliente HTTP Java) para montar essa chamada.

### O fluxo do reCAPTCHA (completo)

```
1. Usuário resolve o desafio no front → Google devolve um TOKEN (g-recaptcha-response)
2. O form envia o token junto com o login → servidor
3. Servidor → POST siteverify (secret key + token) → Google
4. Google responde { "success": true/false, ... }
5. Servidor decide: humano → segue login; bot/inválido → recusa
```

### Passos no código

**1. Dependências no `pom.xml`:** `retrofit`, `converter-gson` (JSON→objeto), `logging-interceptor`.

**2. `RetrofitInicializador`** — cria o cliente apontando para a base do Google:
```java
private static final String BASE_URL = "https://www.google.com/recaptcha/api/";
retrofit = new Retrofit.Builder()
    .baseUrl(BASE_URL)
    .addConverterFactory(GsonConverterFactory.create())
    .build();
```

**3. Interface `GoogleService`** — declara a chamada `POST siteverify`:
```java
public interface GoogleService {
    @POST("siteverify")
    Call<String> enviaToken(@Query("secret") String secret,
                            @Query("response") String response);
}
// (retorno String por enquanto; vira um objeto tipado depois)
```

**4. No `UsuarioController.login`** — pegar o token do clique:
```java
String recaptcha = request.getParameter("g-recaptcha-response");
```

### Por que Retrofit

| Sem Retrofit | Com Retrofit |
|--------------|--------------|
| Montar `HttpURLConnection`, streams, parse manual de JSON | **Interface anotada** (`@POST`, `@Query`) + Gson converte o JSON |
| Muito boilerplate | Declarativo e enxuto |

> 🔑 **A peça que faltava:** só o widget no front (parte 1) **não protege** — um bot ignora o desafio. É esta **validação no servidor** (secret key → `siteverify`) que **confirma** o token e permite **recusar** quem não resolveu. Sem ela, o reCAPTCHA é decorativo.

> 🔒 **A secret key vive no servidor** — ela vai nesta chamada `siteverify`, **nunca** no HTML. (Distinção site key × secret key da parte 1.)

> ⚠️ **Nota de versões:** o curso usa Retrofit `2.3.0` (2017). As libs evoluíram — em projeto real, use versões atuais e confira mudanças de API. O **conceito** (cliente HTTP declarativo validando o token no servidor) permanece igual.

<summary>Ver gabarito comentado</summary>

**Resposta correta: B.** No Retrofit, **`@Query("nome")`** anexa o parâmetro à **query string da URL** (ex.: `siteverify?secret=...&response=...`). É a forma de **enviar** dados na URL da requisição.

**Por que as outras estão erradas:**
- **A** — o oposto: `@Query` **inclui** o parâmetro na requisição, não o descarta.
- **C** — `@Query` é sobre **enviar** (request), não **receber**. O que a app recebe é o **retorno** do método (`Call<String>` / o objeto do JSON de resposta).

> 🔑 **Anotações do Retrofit (mapa rápido):** `@Query` → parâmetro na **URL**; `@Body` → objeto no **corpo**; `@Field`/`@FormUrlEncoded` → corpo **form-urlencoded**; `@Path` → substitui `{trecho}` na URL; `@Header` → cabeçalho. Aqui o `siteverify` aceita os parâmetros na URL, por isso `@Query`.

> 💡 **Curiosidade:** mesmo sendo um `@POST`, os parâmetros vão na **URL** (via `@Query`) — método HTTP e **onde** o parâmetro viaja são coisas independentes (ecoa a lição GET×POST: o método não define sozinho a localização do dado).

</details>

### 🧩 Executando a chamada — `GoogleWebClient`

**1. `getGoogleService()` no `RetrofitInicializador`** (cria a implementação da interface):
```java
public GoogleService getGoogleService() {
    return retrofit.create(GoogleService.class);
}
```

**2. `GoogleWebClient.verifica(...)`** — dispara o POST ao `siteverify`:
```java
public class GoogleWebClient {
    private static final String SECRET = "[Sua secret key]";

    public void verifica(String recaptcha) throws IOException {
        Call<String> token = new RetrofitInicializador()
            .getGoogleService()
            .enviaToken(SECRET, recaptcha);   // secret + token do clique
        token.execute().body();               // execute() = chamada síncrona; body() = resposta
    }
}
```

**3. No `UsuarioController.login`** (após pegar o `g-recaptcha-response`):
```java
new GoogleWebClient().verifica(recaptcha);
```

### O resultado (e por que dá Exception)

Ao logar e clicar no reCAPTCHA, o Google **responde um JSON** — mas declaramos o retorno como **`Call<String>`**, então o Gson **não consegue** converter o JSON num `String` → **Exception**.

> 🔑 **Exception aqui é progresso:** ela **prova** que a comunicação com o Google **funcionou** (a resposta chegou). Falta só **modelar o JSON** num objeto tipado (ex.: classe com `success`, `challenge_ts`, `hostname`) para o Gson desserializar corretamente — **próxima aula**.

| Trecho | Papel |
|--------|-------|
| `retrofit.create(GoogleService.class)` | Gera a implementação concreta da interface |
| `enviaToken(SECRET, recaptcha)` | Monta a requisição (`secret` + `response`) — ainda **não** envia |
| `.execute()` | **Executa** a chamada HTTP (síncrona) |
| `.body()` | Pega o **corpo** da resposta |

> ⚠️ **Onde entra a segurança:** é **aqui** que a validação acontece de fato — a **secret key** (no servidor) + o token vão ao Google, que confirma se foi humano. O próximo passo é **ler o `success`** do JSON e **só então** decidir se o login prossegue.

> 🔴 **Cuidado real:** a `SECRET` está **hardcoded** na classe (didático). Em produção, segredo vai em **variável de ambiente / vault** — nunca commitado no código ([89.md](89.md): segredo não vaza).

### 🔎 Descobrir o JSON — logging interceptor (OkHttp)

> Para saber **como o JSON do Google é estruturado** (e então modelá-lo), interceptamos a requisição com o **`HttpLoggingInterceptor`** e imprimimos o corpo no console.

No construtor do `RetrofitInicializador`:
```java
HttpLoggingInterceptor interceptor = new HttpLoggingInterceptor();
interceptor.setLevel(Level.BODY);                 // loga o corpo da req/resposta

OkHttpClient.Builder client = new OkHttpClient.Builder();
client.addInterceptor(interceptor);

retrofit = new Retrofit.Builder().baseUrl(BASE_URL)
    .addConverterFactory(GsonConverterFactory.create())
    .client(client.build())                       // ← pluga o OkHttp com o interceptor
    .build();
```

> 💡 **Por que via OkHttp?** O Retrofit **não** tem método próprio de logging, mas roda **sobre o OkHttp** — então o interceptor entra no **cliente OkHttp** e o Retrofit o usa via `.client(...)`. `Level.BODY` mostra headers **+ corpo** (útil p/ debug; em produção, cuidado: pode **logar dados sensíveis** — ver [89.md](89.md) logging seguro).

**Resultado:** no console do Eclipse aparece o **JSON de resposta** do `siteverify`, algo como:
```json
{ "success": true, "challenge_ts": "...", "hostname": "..." }
```

> 🔑 **O campo que importa: `success`** (true/false). Agora que **conhecemos a estrutura**, o próximo passo é criar uma **classe** com o atributo `success` para o **Gson desserializar** (em vez de `Call<String>`) — e então **decidir o login** (`success == true` → humano). *(próxima aula)*

> 🧩 **Técnica reutilizável:** "não sei o formato da resposta → **intercepto e logo** o corpo → modelo o objeto". Vale para **qualquer** integração de API, não só reCAPTCHA.

### 📦 Modelar o JSON — classe `Resposta`

Conhecendo o JSON (`{ "success": true, ... }`), criamos uma classe cujo **atributo tem o mesmo nome da chave** — o Gson mapeia automaticamente:

```java
public class Resposta {
    private boolean success;          // = chave "success" do JSON

    public boolean isSuccess() {
        return success;
    }
}
```

Trocar o tipo de retorno de `String` → `Resposta` na interface e no client:

```java
// GoogleService
@POST("siteverify")
Call<Resposta> enviaToken(@Query("secret") String secret, @Query("response") String response);

// GoogleWebClient.verifica(...)
Call<Resposta> token = new RetrofitInicializador().getGoogleService().enviaToken(SECRET, recaptcha);
boolean valido = token.execute().body().isSuccess();   // agora sem Exception
```

> 🔑 **Por que resolve a Exception:** antes, o Gson tentava enfiar um **JSON num `String`** → erro. Agora ele **desserializa** o JSON num objeto `Resposta`, casando `"success"` → campo `success`. Só o **nome do campo** precisa bater com a chave (para nomes diferentes, usa-se `@SerializedName`).

> 🧩 **Falta o último passo:** já temos o `boolean` do `isSuccess()`. A **próxima aula** usa esse valor para **decidir**: `true` → segue o login; `false` → recusa com "reCAPTCHA inválido". Só aí a proteção fica **completa** (front → siteverify → **decisão**).

### 🎯 Decisão final — bloquear o login se não for humano

**1. `verifica` retorna o boolean** (e a classe vira bean gerenciado pelo Spring):
```java
@Component
public class GoogleWebClient {
    private static final String SECRET = "[secret key]";
    public boolean verifica(String recaptcha) throws IOException {
        Call<Resposta> token = new RetrofitInicializador().getGoogleService().enviaToken(SECRET, recaptcha);
        return token.execute().body().isSuccess();   // ← retorna true/false
    }
}
```

**2. Injetar no `UsuarioController` com `@Autowired`** (sem `new`):
```java
@Autowired
private GoogleWebClient cliente;
...
boolean verificaRecaptcha = cliente.verifica(recaptcha);
```

**3. Decidir o fluxo:**
```java
if (verificaRecaptcha) {
    return procuraUsuario(usuario, redirect, model, session);   // humano → segue login
}
redirect.addFlashAttribute("mensagem", "Por favor, comprove que você é humano!");
return "redirect:/usuario";                                     // bot → recusa
```

**Validação:** login da Ana **com** o reCAPTCHA clicado → entra no perfil ✅; **sem** clicar → "comprove que você é humano" ❌.

> 🔑 **Agora a proteção é real (fim do arco):** o valor `success` **decide** o login. Um bot (Burp Intruder) que não resolve o desafio recebe `success:false` → **login recusado** — exatamente o brute-force que quebramos.

### `@Component` + `@Autowired` (por que aqui)

| Anotação | Papel |
|----------|-------|
| **`@Component`** | Marca a classe como **bean** gerenciado pelo Spring (ele cria/gerencia a instância) |
| **`@Autowired`** | Pede ao Spring para **injetar** esse bean — sem `new GoogleWebClient()` |

> 💡 **Injeção de dependência** (Spring): em vez de a classe **criar** suas dependências (`new`), o framework as **fornece**. Facilita troca/teste (ex.: injetar um mock do `GoogleWebClient` nos testes) e centraliza o ciclo de vida.

> 🧩 **Arco reCAPTCHA completo:** front (widget) → token → `siteverify` (secret, via Retrofit) → JSON `{success}` → classe `Resposta` → **`if(success)` decide o login**. Só com **todas** as peças o CAPTCHA protege de verdade.

### ✅ Prova final — o mesmo brute-force do Burp, agora **bloqueado**

Refazemos **exatamente** o ataque do Intruder (interceptar login da Ana → Positions na senha → Payloads com 10 senhas, incluindo `789` → Start Attack).

**Antes (sem reCAPTCHA):** só `789` dava **200** → senha descoberta.
**Agora (com reCAPTCHA):** **nenhuma** senha dá 200 — **inclusive a `789` correta** dá **302** (redirect ao login).

> 🔑 **Por que até a senha certa falha:** o Intruder **reenvia a requisição** trocando só a senha, **sem** resolver o desafio do reCAPTCHA. Sem um token válido, o `siteverify` responde `success:false` → o `if(success)` **recusa** (302) **antes** de checar a senha. O bot **nunca** passa da barreira do CAPTCHA — mesmo acertando a senha.

| | Sem reCAPTCHA | Com reCAPTCHA |
|--|---------------|---------------|
| Senha errada | 302 | 302 |
| **Senha certa (789)** | **200** (vaza!) | **302** (bloqueado ✅) |
| Brute-force automatizado | **funciona** | **neutralizado** |

> 🧠 **A lição do arco inteiro (SQLi + senha + brute-force):** o ataque **manual/pontual** de um humano ainda resolveria o CAPTCHA — a defesa mira a **automação em escala** (o que torna o brute-force viável). Some com **hash forte**, **rate limit** e **MFA** ([89.md](89.md)) para cobrir os demais ângulos. Nenhuma camada sozinha basta; **juntas**, elas encarecem o ataque até deixá-lo inviável.

> 🧭 **Reforço ético:** todo esse ataque foi na **Alura Shows** (lab próprio/autorizado). Só se testa o que é seu ou o que você tem permissão explícita para testar.

| A | **404** — servidor não encontrou o recurso | ❌ |

| D | Valida só e-mail/senha → como estão corretos, **200** e entra no perfil | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: B.** Agora o login checa **três** coisas: e-mail, senha **e** o `success` do reCAPTCHA. Como o Burp Intruder **não resolve** o desafio, o `success` vem `false` → a app **redireciona ao login** = **HTTP 302** — mesmo com a senha **certa** (`789`).

**Por que as outras estão erradas:**
- **A (404)** — o recurso `/login` **existe**; não é "não encontrado". O que muda é o **fluxo** (redirect), não a existência.
- **C (500)** — não há erro de servidor, e reCAPTCHA **funciona local** (registramos `127.0.0.1`, ver quiz do 127.0.0.1). Foi justamente o que testamos.

</details>

### 📝 Quiz Oficial do Curso — O que é a chave `success`?

> **Cenário:** o JSON do `siteverify` traz a chave `success`. O que ela indica?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | `true`/`false` indicando se **a comunicação** com o Google ocorreu | ❌ |
| B | `0`/`1` — sendo **0 = válido** e **1 = inválido** | ❌ |
| **C** | `true`/`false` indicando se o **clique do reCAPTCHA foi validado** (true = válido) | ✅ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: C.** `success` é um **boolean** que diz o **veredito do reCAPTCHA**: `true` = o Google considerou o desafio **válido** (provavelmente humano); `false` = **inválido** (bot/token expirado/errado). É esse campo que o servidor lê para **decidir** se libera o login.

**Por que as outras estão erradas:**
- **A** — não é sobre "a comunicação ter ocorrido": se o JSON chegou, a comunicação **já aconteceu** (independente do valor). `success` avalia o **desafio**, não a conexão.
- **B** — é **boolean** (`true`/`false`), **não** número `0`/`1`. E a lógica está invertida: mesmo se fosse numérico, "válido" seria o positivo, não `0`.

> 🔑 **Cuidado (além do curso):** `success: true` diz apenas que o **token é válido**, não *quão* humano. O **reCAPTCHA v3** acrescenta um **`score`** (0.0–1.0) para você definir um limiar. Aqui (v2) basta o boolean.

</details>

### 📝 Quiz Oficial do Curso — Por que tivemos a Exception?

> **Cenário:** ao logar e clicar no reCAPTCHA, ocorreu uma Exception (antes de criar a classe `Resposta`). Por quê?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | Esquecemos de **executar** a query (segredo + resposta) | ❌ |
| **B** | O Google enviou um **JSON**, mas o retorno estava configurado como **String** | ✅ |
| C | O clique do reCAPTCHA **não foi aceito** pelo Google | ❌ |
| D | A **comunicação** com o Google **não foi estabelecida** | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: B.** A resposta do `siteverify` é **JSON**, mas a `Call` estava tipada como **`Call<String>`** → o Gson **não consegue** converter um objeto JSON num `String` → **Exception**. A correção foi criar a classe **`Resposta`** e usar `Call<Resposta>` (seção acima).

**Por que as outras estão erradas:**
- **A** — a query **foi** executada (`execute()`); tanto que a resposta **chegou** (por isso o erro é de **conversão**, não de "não enviou").
- **C** — o clique ser aceito ou não é o **valor** de `success` (true/false) — não causa Exception. A Exception é **anterior** a conseguirmos ler esse valor.
- **D** — ao contrário: a Exception **prova** que a comunicação **funcionou** (o JSON voltou). O problema é **desserializar** esse retorno.

> 🔑 **Erro de (des)serialização ≠ erro de rede.** "Recebi dados, mas não sei transformá-los no tipo esperado" é diferente de "não recebi nada". Aqui é o primeiro caso — e a solução é **modelar o tipo** (classe `Resposta`), não mexer na conexão.

</details>

## 🧠 Conceitos Aprendidos

| Conceito | Definição |
|----------|-----------|
| **SQL Injection** | Injetar SQL via entrada concatenada na query ([47.md](47.md), [88.md](88.md)) |
| **Teste da aspa simples** | `'` num campo → erro de sintaxe SQL = indício de SQLi |
| **Dado × código** | A falha é o input ser tratado como **código** SQL, não como **dado** |
| **PreparedStatement** | Query com placeholders `?`; separa comando de dados (corrige SQLi) |
| **Parâmetros em JPA/HQL** | Equivalente do PreparedStatement no ORM — nunca concatenar |
| **Login bypass (`x' or 'a'='a`)** | SQLi que força condição sempre-verdadeira p/ autenticar sem senha |
| **Balanceamento de aspas** | Payload precisa deixar aspas **pares/balanceadas** para ser SQL válido; ímpar → erro de sintaxe (não bypass). `x' or 'a'='a` (4, funciona) × `x' or a=a` (3, quebra) |
| **Alura Shows** | Projeto Java/Tomcat/MySQL vulnerável usado no curso |
| **Kali Linux** | VM com ferramentas de pentest — máquina "atacante" do lab |
| **Rede Bridge (VM)** | VM ganha IP na LAN real → alcança o host/Alura Shows |
| **sqlmap** | Ferramenta que **detecta e explora** SQLi automaticamente e **extrai** o banco (`--dump -T -D`) |
| **`--data` (sqlmap)** | Testa parâmetros enviados por **POST** (corpo) — SQLi não depende de GET/POST |
| **GET × POST não corrige SQLi** | Método HTTP não é a causa; a causa é a **concatenação** no código |
| **PreparedStatement (JDBC)** | `?` + `setString(i, valor)` — query e dado **separados**; índice começa em **1** |
| **JPA ≡ PreparedStatement** | Parâmetros nomeados (`:email`) do ORM resolvem a SQLi igual ao PreparedStatement |
| **`EntityManager` / `@PersistenceContext`** | API JPA: `persist` p/ salvar, `createQuery`+`setParameter` p/ consultar com segurança |
| **Validar a correção** | Rodar o sqlmap de novo → "não injetável" confirma que a SQLi foi eliminada |
| **BCrypt** | Hash de senha **lento + salgado**: `gensalt()` + `hashpw()`; verificar com `checkpw()` |
| **Salt** | Aleatório por senha → hashes diferentes p/ senhas iguais; anula rainbow tables |
| **Hash unidirecional** | Não se "descriptografa" senha; compara-se **hash × hash** no login |
| **`BCrypt.checkpw`** | Valida no login: reprocessa a senha digitada com o salt do hash e compara |
| **Login com hash** | Busca pelo **e-mail** (não pela senha) → pega o hash → `checkpw` (não dá p/ comparar hash na query, por causa do salt) |
| **Burp Suite** | Proxy interceptador de tráfego web; **Intruder** automatiza brute-force/fuzzing |
| **Brute-force ≠ hash** | Hash protege o BD vazado, **não** o login; defesa = rate limit + CAPTCHA + MFA ([89.md](89.md)) |
| **reCAPTCHA** | Valida que o login é **humano** → quebra bots/Intruder (front + validação no servidor) |
| **Site key × secret key** | Pública (front, renderiza) × privada (servidor, valida token) — secret nunca no front |
| **`siteverify`** | Endpoint do Google que valida o token do reCAPTCHA (secret + response → success) |
| **Retrofit** | Cliente HTTP Java declarativo (`@POST`/`@Query` + Gson) — usado p/ chamar o `siteverify` |
| **Validação server-side** | O front só coleta o token; **o servidor** confirma com o Google — sem isso, CAPTCHA é decorativo |
| **HttpLoggingInterceptor (OkHttp)** | Loga req/resposta (`Level.BODY`) p/ inspecionar o JSON — cuidado com dados sensíveis |
| **JSON `success`** | Campo do `siteverify` que diz se o reCAPTCHA foi válido (true/false) |
| **Desserialização (Gson)** | Classe `Resposta` com campo de mesmo nome da chave JSON → `Call<Resposta>` (sem Exception); `@SerializedName` p/ nomes diferentes |
| **Decisão do reCAPTCHA** | `if(success)` → segue login; senão → recusa ("comprove que é humano") |
| **`@Component`/`@Autowired`** | Bean gerenciado pelo Spring + injeção de dependência (sem `new`) |

## ✅ Quiz Mental

1. Por que uma **aspa simples** na senha gera erro de sintaxe SQL?
2. O que a Exception **revela** do ponto de vista de segurança?
3. Como se **corrige** a causa (não o sintoma)?
4. Por que deixar a Exception de SQL chegar ao usuário é **duplamente** ruim?

<details>
<summary>Ver respostas</summary>

1. Porque a app **concatena** a entrada na query. A `'` **fecha** a string SQL antes da hora e desbalanceia as aspas → sintaxe inválida → Exception. Prova que o input é interpretado como **SQL**
2. Que **não há validação/parametrização**: se uma aspa quebra a query, um payload real (`' OR 1=1 --`) a **manipula**. É **SQL Injection** — vulnerabilidade a corrigir
3. Com **PreparedStatement** (placeholders `?` + `setString`) ou parâmetros do ORM (JPA/HQL) — o valor trafega como **dado**, nunca como código. (+ validação de entrada e menor privilégio no usuário do banco)
4. (a) **Não corrige** a vulnerabilidade e (b) **vaza informação** ([89.md](89.md)): a mensagem de erro confirma ao atacante que há SQLi e revela detalhes do banco. Erro deve ir para **log interno**, não para o usuário

</details>
