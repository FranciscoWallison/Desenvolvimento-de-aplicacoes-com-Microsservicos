## 💥 XSS — Cross-Site Scripting

> **XSS** é injetar **código (JavaScript)** numa página, que é **executado no navegador de outros usuários**. A app confia na entrada e a **renderiza como HTML/JS** em vez de tratá-la como **texto**.

### Prática — Stored XSS no depoimento

No campo **mensagem** de um depoimento da Alura Shows, em vez de texto, inserimos **script**:

```html
<script>
  document.body.innerHTML = "";              // apaga a página
  var imagem = new Image();
  imagem.src = "[url da imagem]";
  document.body.appendChild(imagem);         // injeta a imagem do "ativista"
</script>
```

**Resultado:** ao **qualquer usuário** abrir a página de depoimentos, o "depoimento" (que é **JS**) **executa** — a página é limpa e a imagem aparece. É um **defacement** via XSS.

### Por que é **Stored** (persistente)

| Tipo de XSS | Onde o payload mora | Alcance |
|-------------|--------------------|---------|
| **Stored / Persistente** ← *este caso* | **Salvo no banco** (o depoimento) | **Todos** que abrem a página |
| **Reflected** | Refletido da **requisição** (ex.: parâmetro na URL) | Quem clicar no link malicioso |
| **DOM-based** | Manipulação de DOM no **próprio front** | Depende do fluxo client-side |

> 🔑 **Stored é o pior caso:** o payload fica **guardado** e atinge **cada visitante** automaticamente — sem precisar enganar ninguém a clicar em nada. O depoimento salvo vira uma **armadilha permanente**.

### 📝 Quiz Oficial do Curso — Qual foi o resultado?

> **Cenário:** inserimos o `<script>` com imagem no campo mensagem do depoimento. O que aconteceu?

| | Alternativa | Veredito |
|--|-------------|----------|
| **A** | A app serve **todas as mensagens do banco** → o JS carrega no navegador de **todos** que abrem a JSP depoimento | ✅ |
| B | A imagem só apareceu **na máquina do atacante** (Kali); os demais viam a página normal | ❌ |
| C | Deu **erro** — a app validou e rejeitou o JavaScript | ❌ |
| D | A imagem apareceu no **Windows** (vítima), mas **não** no Kali (atacante) | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: A.** É **Stored XSS**: o depoimento (que é **JS**) foi **salvo no banco**, e a página lista **todos** os depoimentos para **qualquer** visitante. Logo, o script executa no navegador de **todo mundo** que abrir a página — não só do atacante nem só de uma vítima específica.

**Por que as outras estão erradas:**
- **B** — não é local ao atacante: por ser **stored/servido a todos**, atinge **qualquer** visitante (essa descrição pareceria mais um DOM XSS local, não o caso).
- **C** — **não** houve validação: foi justamente a **falta de escape** que permitiu o ataque. Se validasse, não haveria XSS.
- **D** — atinge **todos** os que carregam a página, **incluindo** o atacante — não é "Windows sim, Kali não".

> 🔑 **A marca do Stored XSS:** *"a app serve o conteúdo salvo para todos"* → **todos** os visitantes são vítimas. Alcance amplo e automático é o que o distingue do Reflected (só quem clica no link).

</details>

### A causa

> O servidor **grava** a mensagem e depois a **devolve dentro do HTML sem escapar** — então o navegador vê `<script>` como **tag executável**, não como texto. É a **mesma falha-raiz do SQLi** ([88.md](88.md)/[90.md](90.md)), num contexto diferente: **dado tratado como código**, agora **no HTML** em vez de no SQL.

### 📝 Quiz Oficial do Curso — O que é XSS?

> **Cenário:** a Alura Shows está sujeita a XSS. Em que consiste o ataque?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | Forçar uma **lista de senhas** para descobrir a senha de outro usuário | ❌ (isso é **brute-force**, [90.md](90.md)) |
| B | Inserir código malicioso num **arquivo de upload** mal validado | ❌ (isso é **upload inseguro**, outra falha) |
| **C** | Inserir **scripts maliciosos** num **site confiável** para comprometer **outros usuários** | ✅ |
| D | Inserir **código SQL** para descobrir a estrutura do banco | ❌ (isso é **SQL Injection**, [90.md](90.md)) |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: C.** XSS = injetar **script** que roda no navegador de **outros usuários** de um site (que eles confiam). O "cross-site" vem daí: o código do atacante executa **no contexto do site legítimo**, contra suas vítimas.

**Por que as outras estão erradas (cada uma é OUTRA vulnerabilidade):**
- **A** — **brute-force** de senha (Burp Intruder, [90.md](90.md)) — nada a ver com injetar script.
- **B** — **upload inseguro de arquivo** — vulnerabilidade real, mas distinta do XSS (que injeta script numa página, não via arquivo).
- **D** — **SQL Injection** ([90.md](90.md)) — injeta SQL no **banco**; XSS injeta JS no **navegador**. Mesma família ("dado vira código"), **alvos diferentes**.

> 🔑 **A palavra-chave é "outros usuários":** SQLi ataca o **banco/servidor**; XSS ataca **os usuários** da aplicação, usando o site confiável como veículo.

</details>

## ⚠️ O impacto real (além da imagem)

O exercício só troca a imagem (defacement), mas XSS **executa JS na sessão da vítima** — o que é grave:

| Ataque via XSS | Efeito |
|----------------|--------|
| **Roubo de cookie/sessão** | `document.cookie` → atacante assume a conta ([89.md](89.md)) |
| **Keylogging / phishing** | Captura o que a vítima digita; injeta um login falso |
| **Ações como a vítima** | Faz requisições autenticadas (curtir, transferir, mudar e-mail) |
| **Defacement / propaganda** | O caso do "ativista" |

> 🔑 Por isso cookies de sessão devem ter **`HttpOnly`** ([89.md](89.md)): o JS injetado **não consegue** ler o cookie. É defesa em profundidade — reduz o dano **mesmo** se um XSS passar.

## 🧹 Limpeza — remover o depoimento malicioso

> Antes de corrigir, apaga-se o payload já **salvo** no banco (Stored XSS = ele persiste!).

```sql
delete from owasp.Depoimento where mensagem like "<script>%";
```

- **MySQL Workbench:** desmarcar `Edit → Preferences → SQL Editor → Safe Updates` → **Reconnect to Server** → rodar o `delete`. (O *Safe Updates* bloqueia `DELETE` sem `WHERE` por chave — proteção do Workbench contra apagar demais.)

> 🔑 **A pegadinha do Stored XSS:** corrigir o **código** não limpa o que **já está no banco**. O payload continuaria disparando até ser **removido**. Por isso: **limpar os dados infectados** + **corrigir a causa** — os dois.

## ✅ A correção (o que vem no curso)

> A raiz é **não renderizar entrada como HTML**. As defesas:

| Defesa | O que faz |
|--------|-----------|
| **Output encoding / escaping** | Ao exibir, converter `<` `>` `"` em entidades (`&lt;`…) → `<script>` vira **texto**, não tag. É a correção principal |
| **Validação de entrada** | Rejeitar/limpar conteúdo perigoso na entrada (defesa secundária) |
| **CSP (Content-Security-Policy)** | Header que restringe **quais scripts** podem rodar → bloqueia inline/externos não autorizados |
| **`HttpOnly` no cookie** | Impede o JS de ler o cookie de sessão (limita o dano) |
| **Bibliotecas de sanitização** | Ex.: OWASP Java Encoder, para escapar por contexto (HTML, atributo, JS, URL) |

> 💡 **Escapar na saída > filtrar na entrada:** o mesmo dado pode ser seguro num contexto e perigoso em outro; o **encoding correto no ponto de exibição** é o que mais confiavelmente mata o XSS. (JSP: `<c:out>` já escapa; concatenar HTML "na mão" é o perigo.)

### 🛠️ A correção do curso — `DepoimentoValidator` (validação de entrada)

O curso implementa a **interface `Validator` do Spring** para **rejeitar** títulos/mensagens que contenham `<` ou `>` (impedindo montar `<script>`):

```java
@Component
public class DepoimentoValidator implements Validator {

    @Override
    public boolean supports(Class<?> clazz) {
        return Depoimento.class.isAssignableFrom(clazz);   // este validador cuida de Depoimento
    }

    @Override
    public void validate(Object target, Errors errors) {
        Depoimento depoimento = (Depoimento) target;
        String titulo = depoimento.getTitulo();
        String mensagem = depoimento.getMensagem();

        if (titulo.contains("<") || titulo.contains(">"))
            errors.rejectValue("titulo", "errors.titulo");
        if (mensagem.contains("<") || mensagem.contains(">"))
            errors.rejectValue("mensagem", "errors.mensagem");
    }
}
```

| Método | Papel |
|--------|-------|
| `supports(clazz)` | Diz ao Spring **para qual tipo** este validador serve (`Depoimento`) |
| `validate(target, errors)` | Faz a checagem; `errors.rejectValue("campo", "codigo")` marca o campo inválido com um **código de mensagem** (o texto vem de um arquivo de mensagens — próxima aula) |

> 🔑 **Sem `<` nem `>`, não há tag** — logo não dá para injetar `<script>`. É uma **validação de entrada** simples e eficaz **para este caso**.

### ⚖️ Nota crítica: bloquear `<`/`>` é defesa parcial

Essa abordagem **funciona no contexto do curso**, mas tem limites importantes — vale registrar:

- **É blocklist (lista de proibidos), não a defesa canônica.** A correção mais robusta de XSS é **escapar na saída** (output encoding, `<c:out>`/OWASP Encoder). Validar entrada é **camada extra**, não substituto.
- **Nem todo XSS precisa de `<`/`>`.** Em contextos de **atributo** ou dentro de `<script>`, dá para injetar sem tag (ex.: `" onmouseover=alert(1)`, `javascript:`). Bloquear só `< >` não cobre esses casos.
- **Pode rejeitar entrada legítima** (um depoimento com "5 < 10" ou "R$ 3 > R$ 2" seria barrado) — falso-positivo de usabilidade.

> 🔑 **O ideal (defesa em profundidade):** **escapar na saída** (principal) **+** validar/sanitizar na entrada (secundária) **+** CSP **+** `HttpOnly`. O validador do curso é um bom **primeiro passo didático**; num sistema real, não confie **só** nele.

### 🔌 Ligando tudo — mensagens + `@Valid` + exibição

O validador só age se estiver **plugado** no fluxo do Spring MVC. Os passos:

**1. Arquivo de mensagens** (`WEB-INF/messages.properties`, UTF-8) — o **texto** por trás dos códigos do `rejectValue`:
```properties
errors.titulo = O título passado não é válido!
errors.mensagem = A mensagem passada não é válida!
```

**2. Registrar o `MessageSource`** (config Spring) — diz de onde ler as mensagens:
```java
@Bean
public MessageSource messageSource() {
    ReloadableResourceBundleMessageSource bundle = new ReloadableResourceBundleMessageSource();
    bundle.setBasename("/WEB-INF/messages");   // → messages.properties
    bundle.setDefaultEncoding("UTF-8");
    return bundle;
}
```

**3. Ligar o validador ao controller** (`@InitBinder`):
```java
@InitBinder
public void initBinder(WebDataBinder binder) {
    binder.setValidator(new DepoimentoValidator());
}
```

**4. Disparar a validação** com `@Valid` + capturar o resultado em `BindingResult`, e **não salvar se houver erro**:
```java
public String enviaMensagem(@Valid @ModelAttribute("depoimentos") Depoimento depoimento,
                            BindingResult result, RedirectAttributes redirect, Model model) {
    chamaPostsDoBanco(model);
    if (result.hasErrors()) {
        return "depoimento";          // volta ao form mostrando os erros (NÃO persiste)
    }
    dao.salvaDepoimento(depoimento);
    return "redirect:/depoimento";
}
```

**5. Exibir os erros na JSP** (`<form:errors>` por campo):
```jsp
<form:errors path="titulo" cssClass="error"/>
<form:errors path="mensagem" cssClass="error"/>
```

**Resultado:** inserir `<script>` no título/mensagem → validação falha → a app **não salva** e mostra *"O título passado não é válido!"*. O XSS foi **bloqueado na entrada**. ✅

### O papel de cada peça

| Peça | Função |
|------|--------|
| `messages.properties` | **Texto** das mensagens (por código) — permite i18n |
| `MessageSource` (`setBasename`) | Diz ao Spring **onde** achar as mensagens |
| `@InitBinder` + `setValidator` | **Pluga** o `DepoimentoValidator` no controller |
| `@Valid` | **Dispara** a validação ao receber o objeto |
| `BindingResult result` | **Recebe** os erros (tem de vir **logo após** o `@Valid`) |
| `result.hasErrors()` | Decide **não persistir** e voltar ao form |
| `<form:errors path=...>` | **Renderiza** a mensagem do campo na tela |

> ⚠️ **Ordem importa:** o `BindingResult` **deve** vir **imediatamente após** o parâmetro `@Valid` na assinatura — senão o Spring lança exceção em vez de popular os erros.

> 🧩 **Ciclo XSS completo (neste doc):** **explorar** (stored XSS no depoimento) → **limpar** o BD infectado → **corrigir** (validator bloqueia `<`/`>` + mensagens + `@Valid`) → **e a defesa canônica** (escapar na saída/CSP/`HttpOnly`, que o curso não cobre mas registramos).

### 📝 Quiz Oficial do Curso — O que faz o método `supports`?

> **Cenário:** implementamos a interface `Validator` (métodos `supports` e `validate`). O que o **`supports`** faz?

| | Alternativa | Veredito |
|--|-------------|----------|
| **A** | Recebe a **classe** do objeto e retorna se o validador **consegue lidar** com objetos dessa classe | ✅ |
| B | Recebe o objeto **`Errors`** onde guardamos as falhas | ❌ |
| C | Recebe o **`target`** (objeto a validar) **e** o `Errors` | ❌ |
| D | Recebe o **objeto** a validar (`Object`) e faz o cast para `Depoimento` | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: A.** `supports(Class<?> clazz)` recebe a **classe** e devolve um **boolean**: "este validador sabe validar objetos **deste tipo**?". No código: `return Depoimento.class.isAssignableFrom(clazz);` — verdadeiro só para `Depoimento`. O Spring chama o `supports` **antes** de validar, para saber se aquele validador se aplica.

**Por que as outras estão erradas (descrevem o `validate`, não o `supports`):**
- **B / C / D** — todas falam de **`validate(Object target, Errors errors)`**: recebe **o objeto** (`target`, com cast p/ `Depoimento`) **e** o **`Errors`** (onde se registram as falhas). Esse é o **outro** método da interface.

> 🔑 **A divisão da interface `Validator`:** **`supports`** = "*posso* validar esta classe?" (seleção); **`validate`** = "*valide* este objeto e registre os erros" (execução). São papéis distintos — o quiz mistura os dois de propósito.

</details>

### 📝 Quiz Oficial do Curso — O que faz o `if` do `validate`?

> ```java
> if (titulo.contains("<") || titulo.contains(">")) {
>     errors.rejectValue("titulo", "errors.titulo");
> }
> ```

| | Alternativa | Veredito |
|--|-------------|----------|
| A | Rejeita se o título tiver `<` **E também** `>` | ❌ |
| B | Rejeita se o título **não** tiver `<` ou `>` | ❌ |
| **C** | Rejeita se o título tiver `<` **ou** `>` (qualquer um) | ✅ |
| D | Rejeita se tiver `<` ou `>` e mostra a mensagem "errors.titulo" (o texto literal) | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: C.** O operador **`||` (OU lógico)** faz o `if` ser verdadeiro se **qualquer um** dos símbolos estiver presente — `<` **ou** `>`. Basta **um** para o `rejectValue` marcar o título como inválido.

**Por que as outras estão erradas:**
- **A** — exigiria **`&&`** (E) e os **dois** símbolos juntos. Com `||`, **um só** já rejeita.
- **B** — **inverteria** a lógica (rejeitar quando **não** contém) — seria um `!contains(...)`. Aqui é o contrário: rejeita quando **contém**.
- **D** — `"errors.titulo"` **não é a mensagem** exibida; é um **código** que o Spring usa para **buscar** o texto num arquivo de mensagens (`messages.properties`). A mensagem real é configurada depois (próxima aula).

> 🔑 **`rejectValue("campo", "codigo")`:** 1º arg = **campo** inválido; 2º arg = **código da mensagem** (chave), não o texto. Separar código do texto permite i18n (traduções) e centralizar as mensagens.

</details>

### 📝 Quiz Oficial do Curso — Por que o `@Bean MessageSource`?

> ```java
> @Bean
> public MessageSource messageSource(){
>     ReloadableResourceBundleMessageSource bundle = new ReloadableResourceBundleMessageSource();
>     bundle.setBasename("/WEB-INF/messages");
>     bundle.setDefaultEncoding("UTF-8");
>     return bundle;
> }
> ```
> **Por que adicionamos esse método na `CasaDeShowConfiguration`?**

| | Alternativa | Veredito |
|--|-------------|----------|
| **A** | Para o Spring MVC saber que deve usar o **`messages.properties`** (em `WEB-INF`) para exibir as mensagens de erro | ✅ |
| B | Para **criar** a classe `DepoimentoValidator` e assim validar `<`/`>` no título e mensagem | ❌ |
| C | Para informar ao Spring MVC que **não** fazemos validação no projeto | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: A.** O `MessageSource` é a peça que **resolve códigos → texto**. O `rejectValue("titulo", "errors.titulo")` do validador registra apenas o **código** `errors.titulo`; sem um `MessageSource` configurado, o Spring não saberia **onde** buscar o texto correspondente. O `setBasename("/WEB-INF/messages")` aponta justamente para o `messages.properties` — é o que faz *"O título passado não é válido!"* aparecer na tela.

**Por que as outras estão erradas:**
- **B** — confunde as peças: quem cria/pluga o validador é a classe `DepoimentoValidator` (`@Component`) + o `@InitBinder`. O `MessageSource` **não cria validador nenhum**; ele só fornece o **texto** das mensagens depois que a validação falha.
- **C** — é o **oposto** do que ocorre: registrar o `MessageSource` só faz sentido **porque há** validação produzindo erros a exibir. Ele não "desliga" validação alguma.

> 🔑 **A cadeia da mensagem de erro:** `rejectValue("campo","codigo")` (validador) → **`MessageSource`** acha o arquivo (`setBasename`) → **`messages.properties`** tem o texto (`codigo = texto`) → **`<form:errors>`** renderiza na JSP. O `@Bean MessageSource` é o **elo do meio** — sem ele, a corrente quebra e o código nunca vira texto.

</details>

### 📝 Quiz Oficial do Curso — Que ajuste no `messages.properties`?

> **Cenário:** criamos o `messages.properties` com as mensagens, mas precisamos **alterar uma configuração nesse arquivo** para as mensagens saírem certas na JSP. Qual foi?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | Indicar o **idioma padrão** (português Brasil) | ❌ |
| B | Definir a codificação como **ISO-8859-1** | ❌ |
| **C** | Definir a codificação como **UTF-8** → caracteres especiais exibidos corretamente | ✅ |
| D | Restringir a mensagem só a **browsers em pt-BR** | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: C.** O ajuste foi a **codificação para UTF-8**. As mensagens têm acentos (*"O tít**u**lo passado n**ã**o é v**á**lido!"*); sem UTF-8, esses caracteres apareceriam corrompidos (*"nÃ£o"*, *"vÃ¡lido"* — mojibake). É o **par** do `bundle.setDefaultEncoding("UTF-8")` no `MessageSource`: **os dois lados precisam concordar** — o arquivo salvo em UTF-8 **e** o `MessageSource` lendo como UTF-8.

**Por que as outras estão erradas:**
- **A / D** — o problema **não é idioma**. Não há i18n com múltiplos locales aqui (não existe `messages_pt_BR.properties` vs `messages_en.properties`); só um arquivo. Restringir por idioma do browser (**D**) nem é papel do `messages.properties` — e esconderia a mensagem de quem não usa pt-BR.
- **B** — **ISO-8859-1** (Latin-1) é o **oposto** do que foi feito. Historicamente o `.properties` do Java assume ISO-8859-1, e é justamente por isso que se **força UTF-8** — para os acentos não quebrarem. Escolher ISO-8859-1 manteria (ou causaria) o problema.

> 🔑 **Encoding tem de bater nas duas pontas:** arquivo salvo em UTF-8 **+** `setDefaultEncoding("UTF-8")` no `MessageSource`. Se só um lado for UTF-8, os acentos viram *mojibake*. (No Java clássico, `.properties` era ISO-8859-1 e exigia `native2ascii`/`\uXXXX`; o `ReloadableResourceBundleMessageSource` com `setDefaultEncoding` dispensa isso.)

</details>

## 🔐 Perfis de usuário (ROLES) e autorização

> A Alura Shows atribui o perfil **`ROLE_USER`** a quem se cadastra. **ROLES** (papéis) são a base do **controle de acesso baseado em papéis (RBAC)**: em vez de decidir permissões usuário-a-usuário, agrupa-se por **papel** (`ROLE_USER`, `ROLE_ADMIN`…) e restringe-se cada parte do sistema a um conjunto de papéis.

### Autenticação × Autorização (não confundir)

| | Pergunta que responde | Exemplo na Alura Shows |
|--|----------------------|------------------------|
| **Autenticação** (*authn*) | *Quem é você?* | login com e-mail/senha em hash ([90.md](90.md)) |
| **Autorização** (*authz*) | *O que você **pode** fazer?* | `ROLE_USER` vê depoimentos; `ROLE_ADMIN` administra |

> 🔑 As ROLES são a camada de **autorização** — só entram em jogo **depois** que a autenticação já disse quem é o usuário. As duas partes 1 e 2 do curso cobrem, juntas, os dois lados: **provar identidade** (parte 1) e **limitar poderes** (parte 2).

### 📝 Quiz Oficial do Curso — Por que ter diferentes ROLES?

> **Cenário:** ao se cadastrar, o usuário recebe `ROLE_USER`. Por que é importante ter diferentes perfis (ROLES) numa aplicação?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | Evitar **sobrecarga de acessos** na aplicação | ❌ |
| **B** | **Permitir ou negar** o acesso a determinadas partes do sistema | ✅ |
| C | Ter **melhor performance** nas queries de consulta ao banco | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: B.** ROLES existem para **autorização**: definir **quem pode acessar o quê**. Um `ROLE_USER` pode escrever um depoimento; só um `ROLE_ADMIN` pode moderar/excluir, acessar o painel etc. É assim que se aplica o **menor privilégio** — cada papel recebe **apenas** o acesso de que precisa.

**Por que as outras estão erradas:**
- **A** — ROLE é sobre **permissão**, não sobre **carga/escala**. Sobrecarga de acessos se resolve com infraestrutura (rate limiting, cache, balanceamento), não com papéis de usuário.
- **C** — ROLE **não** otimiza query. Performance de consulta vem de índices, modelagem e boas queries. Confundir controle de acesso com tuning de banco é a pegadinha.

> 🔑 **ROLE = fronteira de autorização, não de desempenho.** É o mecanismo que faz cumprir o **menor privilégio** e evita o **Broken Access Control** (falta de checagem de permissão — [89.md](89.md), onde vimos IDOR e authz a nível de função × objeto). Sem papéis bem aplicados, qualquer usuário autenticado poderia fazer o que só um admin deveria.

</details>

### 💥 Prática — virar ADMIN pelo formulário (Mass Assignment)

> **Ataque:** o form de cadastro faz **binding direto** da entidade `Usuario` — que tem o atributo **`roles`**. Se o usuário conseguir mandar `roles` na requisição, ele **escolhe o próprio perfil**. Basta injetar um campo escondido antes de enviar.

**Cenário do lab — cadastro da "Joviane"** (nome: Joviane, e-mail: joviane@gmail.com, senha: 123456):

1. **Antes** de clicar em *Registrar*, abrir o **DevTools** (botão direito → *Inspecionar*) e achar o `<form id="register-form">`.
2. Botão direito no `<form>` → **Edit as HTML** e inserir dentro dele um campo **hidden** com o perfil desejado:
   ```html
   <input type="hidden" name="roles[0].name" value="ROLE_ADMIN"/>
   ```
   > O `name="roles[0].name"` casa **exatamente** com o caminho da propriedade que o Spring faz bind: `usuario.getRoles().get(0).setName(...)`. É por isso que funciona — o servidor **aceita** esse campo como se fosse legítimo.
3. Clicar em **Registrar**.
4. Conferir no banco (`Usuario_Role`):
   ```sql
   select * from Usuario_Role;   -- Linux/Mac; no Windows: botão direito na tabela → Select Rows
   ```
   → a Joviane aparece associada a **`ROLE_ADMIN`** (além do `ROLE_USER`).
5. Acessar o painel restrito `http://127.0.0.1:8080/alura-shows/admin` com joviane@gmail.com / 123456 → **login no admin aceito**. 🚨

**Resultado:** um usuário comum se **auto-promoveu a administrador** apenas editando o HTML no navegador — sem tocar no servidor.

### 🐞 A vulnerabilidade — Mass Assignment / Over-posting

> **Mass Assignment** (ou *over-posting* / *autobinding*): a app faz bind de **todos** os campos da requisição direto num **objeto de domínio**, incluindo campos **sensíveis** que o usuário **nunca deveria** controlar (aqui, `roles`).

| Aspecto | Detalhe |
|---------|---------|
| **Causa-raiz** | Entidade `Usuario` (com `roles`) usada **diretamente** como *command object* do form → o cliente controla campos internos |
| **Classe OWASP** | **Broken Access Control** / API6-ish *Mass Assignment* — mesma família do [89.md](89.md) |
| **Impacto** | **Escalonamento de privilégio** (user → admin): quebra total da autorização |
| **Por que o HTML "confiável" não protege** | O form original não tinha o campo `roles`, mas o **servidor aceita** qualquer campo que chegue. Segurança **no cliente não existe** — o atacante controla o request ([90.md](90.md), lição do POST não corrigir SQLi) |

> 🔑 **Mesma doença de sempre: confiar na entrada.** No SQLi a entrada virou comando no banco; no XSS, script no navegador; aqui, a entrada **vira estado de autorização**. O campo `roles` estar *ausente da tela* não o torna *ausente do bind* — "não mostrar" ≠ "não aceitar".

### ✅ Como se defende (o que o curso deve corrigir a seguir)

| Defesa | Como |
|--------|------|
| **DTO / command object dedicado** | Não fazer bind na entidade `Usuario`. Usar um `UsuarioForm` com **só** `nome`, `email`, `senha`; o `roles` **nem existe** ali. Definir a role **no servidor** (`ROLE_USER` fixo no cadastro) |
| **Allow-list de campos** (`@InitBinder`) | `binder.setAllowedFields("nome","email","senha")` — ou `setDisallowedFields("roles")` — para o Spring **ignorar** campos não permitidos |
| **`@JsonIgnore` / anotações** (APIs REST) | Marcar campos sensíveis como não-bindáveis na desserialização |
| **Atribuir role no back-end** | A role de um novo cadastro é **regra de negócio**, definida no service — **nunca** vinda do request |

> 💡 **Regra de ouro:** o cliente escolhe **dados**, o servidor escolhe **privilégios**. Qualquer campo que decida *permissão/estado interno* (role, `isAdmin`, `saldo`, `id` de dono) tem de ser **atribuído no servidor**, jamais aceito do form.

### 📝 Quiz Oficial do Curso — O que é Mass Assignment?

> **Cenário:** a Alura Shows estava vulnerável a **Mass Assignment**. Em que consiste esse ataque?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | Alterar o **redirecionamento** para um site falso parecido com o original | ❌ (isso é *phishing* / open redirect) |
| B | Inserir **SQL** para ver a estrutura do banco | ❌ (isso é **SQL Injection**, [90.md](90.md)) |
| C | **Forçar várias senhas** para descobrir a de outro usuário | ❌ (isso é **brute-force**, [90.md](90.md)) |
| **D** | Um usuário **alterar atributos de uma classe modelo** manipulando os **parâmetros da requisição HTTP** | ✅ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: D.** Mass Assignment é exatamente **manipular os parâmetros do request** para gravar atributos da **classe de modelo** que o usuário não deveria controlar — foi o que fizemos ao injetar `roles[0].name=ROLE_ADMIN` e mexer no atributo `roles` da entidade `Usuario`.

**Por que as outras estão erradas (cada uma é OUTRO ataque):**
- **A** — **phishing / open redirect**: enganar a vítima levando-a a um site falso. Nada a ver com bind de atributos.
- **B** — **SQL Injection** ([90.md](90.md)): dado vira comando **no banco**. Mass Assignment não toca em SQL — abusa do **binding** do framework.
- **C** — **brute-force** ([90.md](90.md)): tentar muitas senhas. É ataque à **autenticação**, não ao mapeamento request→objeto.

> 🔑 **A assinatura do Mass Assignment:** *"parâmetro da requisição → atributo do objeto que eu não deveria poder setar"*. O framework faz o bind automático **cego** e o cliente aproveita para preencher campos internos (role, `isAdmin`, `id` de dono).

</details>

### 📝 Quiz Oficial do Curso — O que é `roles[0].name`?

> **Cenário:** o campo injetado foi `name="roles[0].name" value="ROLE_ADMIN"`. O que é exatamente o **`roles[0].name`**?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | A classe `Usuario` tem um atributo **chamado literalmente** `roles[0].name` | ❌ |
| **B** | `Usuario` tem `roles` (**`List<Role>`**); `Role` tem `name`. O caminho navega: **`roles[0].name`** = o `name` do 1º `Role` da lista | ✅ |
| C | A classe **`Role`** tem um atributo chamado `roles[0].name` | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: B.** `roles[0].name` é um **caminho de propriedade aninhada** que o Spring resolve passo a passo:

```
usuario.getRoles()      → a List<Role> do Usuario
        .get(0)         → roles[0]  = o 1º elemento da lista
        .setName(...)   → .name     = o atributo name daquele Role
```

Ou seja: `roles` é atributo de **`Usuario`** (uma **lista** de `Role`), `[0]` é o **índice** na lista, e `name` é atributo de **`Role`**. Por isso o value `ROLE_ADMIN` cai em `usuario.roles[0].name`.

**Por que as outras estão erradas:**
- **A** — `roles[0].name` **não é um nome de atributo** único; é uma **expressão de navegação** (`.` = "entra no objeto", `[0]` = "índice da lista"). Nenhuma classe tem um campo com esse nome literal.
- **C** — inverte a posse: quem tem o `name` é **`Role`**, mas quem tem a **lista `roles`** é **`Usuario`**. O caminho **começa** em `Usuario` (`roles`) e **termina** em `Role` (`name`).

> 🔑 **Notação de data binding do Spring:** `.` desce um nível de propriedade e `[i]` indexa coleção/array. É o mesmo mecanismo que preenche formulários legítimos — o ataque só **reaproveita** essa navegação para chegar a um campo que a tela não expunha.

</details>

### 🛡️ A correção — `UsuarioDTO` (bloqueando o Mass Assignment)

> **A ideia:** parar de fazer bind na **entidade `Usuario`** (que tem `roles`) e fazer bind num **DTO** (*Data Transfer Object*) que expõe **só** os campos esperados do formulário. Sem `roles` no alvo do bind, **não há onde** o `roles[0].name` cair → o campo malicioso é **ignorado**.

**1. Classe `UsuarioDTO`** — só os 4 campos do form, e **só setters** (o Spring usa setters no bind; getters não são necessários aqui):
```java
public class UsuarioDTO {
    private String email;
    private String senha;
    private String nome;
    private String nomeImagem;
    // setEmail / setSenha / setNome / setNomeImagem  (Eclipse: CTRL+3 → "ggas" → Select Setters)

    public Usuario montaUsuario() {                       // DTO → entidade
        return new Usuario(email, senha, nome, nomeImagem);
    }
}
```

**2. Novo construtor em `Usuario`** (recebe só os campos seguros — **`roles` fica de fora**):
```java
public Usuario(String email, String senha, String nome, String nomeImagem) {
    this.email = email;  this.senha = senha;
    this.nome = nome;    this.nomeImagem = nomeImagem;
}
```

**3. `UsuarioController.registrar`** — faz bind no **DTO**, depois converte:
```java
@RequestMapping(value = "/registrar", method = RequestMethod.POST)
public String registrar(MultipartFile imagem,
        @ModelAttribute("usuarioRegistro") UsuarioDTO usuarioDTO, ...) {

    Usuario usuarioRegistro = usuarioDTO.montaUsuario();   // objeto Usuario montado no servidor
    ...
}
```

**Teste (usuário "Pedro"):** repetindo o mesmo `<input hidden name="roles[0].name" value="ROLE_ADMIN">` → Pedro é cadastrado **só com `ROLE_USER`** e o login no `/admin` é **negado** ("permissão negada"). Ataque **bloqueado**. ✅

### Por que o DTO resolve (e o que ele é de verdade)

| Antes (vulnerável) | Depois (com DTO) |
|--------------------|------------------|
| Bind direto na entidade `Usuario` (**tem `roles`**) | Bind no `UsuarioDTO` (**não tem `roles`**) |
| `roles[0].name` acha destino → grava `ROLE_ADMIN` | `roles[0].name` **não tem destino** → ignorado |
| Cliente escolhe o próprio perfil | Perfil (`ROLE_USER`) definido **no servidor** |

> 🔑 **O DTO é uma *allow-list por construção*:** a **forma** da classe já é a lista de campos permitidos — o que não está nela **não pode** ser preenchido pela requisição. É mais robusto que uma blocklist (`setDisallowedFields("roles")`), que exige lembrar de proibir **cada** campo perigoso; no DTO, o padrão é **negar** (só entra o que foi explicitamente declarado).

> 💡 **Bônus de arquitetura (além da segurança):** separar o **modelo de entrada** (DTO) do **modelo de domínio/persistência** (`Usuario`) é boa prática independentemente do ataque — desacopla o contrato do formulário da tabela do banco, evita expor campos internos e deixa a validação/mapeamento explícitos. Segurança **e** design saem ganhando. (O `@ModelAttribute("usuarioRegistro")` tem de casar com o `modelAttribute`/`commandName` da JSP para o bind e o `<form:errors>` funcionarem.)

### 📝 Quiz Oficial do Curso — Por que criamos o `UsuarioDTO`?

> **Cenário:** passamos a fazer o bind do form de registro no `UsuarioDTO` em vez da entidade `Usuario`. Por quê?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | A app tinha **problema de performance** nas queries do Hibernate | ❌ |
| B | `Usuario` **não tinha** todos os atributos necessários para o registro | ❌ |
| **C** | `Usuario` tem o atributo **`roles`**, que **não deve** ser manipulado pelo usuário | ✅ |
| D | `Usuario` **não tinha** o atributo `roles`, necessário para o registro | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: C.** O DTO existe para **tirar `roles` do alvo do bind**. A entidade `Usuario` **tem** `roles` — e é justamente por isso que o Mass Assignment funcionava. O `UsuarioDTO` expõe **só** os campos que o usuário pode preencher (email, senha, nome, nomeImagem); `roles` fica **fora**, definido no servidor.

**Por que as outras estão erradas:**
- **A** — DTO aqui é **segurança**, não performance. (DTOs *podem* ajudar performance em outros contextos — ex.: projeção de campos numa consulta — mas **não é** o motivo aqui.)
- **B** — ao contrário: `Usuario` tem atributos **demais** para o form (inclusive `roles`). O problema era **excesso** de campos bindáveis, não falta.
- **D** — factualmente **errado**: `Usuario` **tem** `roles` (foi o campo explorado). E `roles` **não** deve vir do formulário — é atribuído pelo servidor.

> 🔑 **O critério do DTO:** exponha ao bind **só o que o usuário pode legitimamente informar**. Campos de **autorização/estado interno** (`roles`, `isAdmin`, `saldo`) nunca entram no DTO de entrada — o servidor os define.

</details>

### 📝 Quiz Oficial do Curso — Qual foi o resultado (com o DTO)?

> **Cenário:** já com o `UsuarioDTO`, o Pedro repetiu o ataque (`roles[0].name=ROLE_ADMIN`). O que aconteceu?

| | Alternativa | Veredito |
|--|-------------|----------|
| **A** | Pedro foi cadastrado **só com `ROLE_USER`** | ✅ |
| B | Pedro foi cadastrado com **`ROLE_ADMIN`** | ❌ |
| C | Pedro ficou com **os dois** perfis (`ROLE_ADMIN` + `ROLE_USER`) | ❌ |
| D | A aplicação lançou uma **Exception** dizendo que a manipulação é inválida | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: A.** Com o bind no `UsuarioDTO` (que **não tem** `roles`), o campo `roles[0].name` **não tem destino** e é simplesmente **ignorado**. O Pedro é criado via `montaUsuario()` e recebe o perfil padrão **`ROLE_USER`** (definido no servidor). Login no `/admin` → **negado**.

**Por que as outras estão erradas:**
- **B / C** — o ataque **falhou**: sem `roles` no DTO, não há como injetar `ROLE_ADMIN`. Ele não vira admin (B) nem acumula papéis (C).
- **D** — **não** houve exceção. É um detalhe importante do Spring: por padrão, **parâmetros desconhecidos no bind são silenciosamente ignorados** (não quebram a requisição). Por isso o ataque falha **sem erro** — o campo malicioso some sem barulho, em vez de derrubar a aplicação.

> 🔑 **Falha segura e silenciosa:** o DTO não *rejeita* o campo extra com erro — ele simplesmente **não o aceita**. Do ponto de vista do atacante, o `roles[0].name` "sumiu". É o comportamento desejado: sem estado sensível bindável, o over-posting não tem superfície.

### 🌱 Alternativa nativa do Spring — `@InitBinder` + `setAllowedFields`

> O DTO funciona em **qualquer** framework. Mas, no Spring, dá para resolver com **menos código** usando o `WebDataBinder`: uma **allow-list de campos** direto no controller. Aí pode-se **voltar a fazer bind na entidade `Usuario`**.

```java
@InitBinder
public void initBinder(WebDataBinder binder) {
    binder.setAllowedFields("nome", "email", "senha", "nomeImagem");   // só estes podem vir do form
}
```

Com isso, o `registrar` volta a receber a **entidade** e a conversão do DTO some:
```java
@RequestMapping(value = "/registrar", method = RequestMethod.POST)
public String registrar(MultipartFile imagem,
        @ModelAttribute("usuarioRegistro") Usuario usuarioRegistro, ...) {
    // Usuario usuarioRegistro = usuarioDTO.montaUsuario();  ← removida
    ...
}
```

**Teste (usuário "Rodrigo"):** mesmo `roles[0].name=ROLE_ADMIN` → o `roles` **não está** na allow-list, então o Spring **não reflete** esse campo na entidade. Rodrigo fica só com **`ROLE_USER`**; `/admin` **negado**. ✅

> 🧩 **Já vimos o `@InitBinder`:** é o **mesmo hook** usado para plugar o `DepoimentoValidator` (seção do XSS). Ele intercepta o `WebDataBinder` **antes** do bind — serve tanto para **registrar validador** quanto para **restringir campos** (`setAllowedFields`).

### ⚖️ DTO × `setAllowedFields` — qual usar?

| | **DTO** | **`setAllowedFields`** |
|--|---------|------------------------|
| **Portabilidade** | Qualquer framework | **Só Spring** |
| **Código** | Mais classes (DTO + `montaUsuario` + construtor) | 3 linhas no controller |
| **Alvo do bind** | Objeto **sem** o campo sensível | A **própria entidade** (com `roles`) — protegida pela lista |
| **Bônus de design** | Desacopla entrada × domínio | Nenhum — a entidade volta a ser command object |
| **Risco de manutenção** | Baixo (o campo *nem existe* no DTO) | **Você tem de manter a lista** — esqueceu de listar/atualizar? o default de campos volta a passar |

> 🔑 **Ambas são allow-list; a diferença é *onde* mora a lista.** No DTO, a lista é a **própria forma da classe** (structural). No `setAllowedFields`, é uma **string a manter** no binder (declarativa). Existe também `setDisallowedFields("roles")` (**blocklist** — mais frágil: protege só o que você lembrar de proibir). Prefira **allow-list**.

> 💡 **Defesa mais forte = controle de autorização, não só de bind.** Nenhuma das duas substitui a regra de ouro: a **role de um novo cadastro deve ser fixada no servidor** (`ROLE_USER`), nunca derivada do request. `setAllowedFields`/DTO impedem o *over-posting*; atribuir a role no back-end garante o resultado **mesmo** que uma dessas barreiras falhe.

### 📝 Quiz Oficial do Curso — O que faz o `setAllowedFields`?

> **Cenário:** no Spring, usamos `setAllowedFields` para evitar o Mass Assignment. O que exatamente esse método faz?

| | Alternativa | Veredito |
|--|-------------|----------|
| **A** | Especifica **quais atributos** da classe modelo o usuário **pode** manipular | ✅ |
| B | Foi usado **junto com** o `UsuarioDTO` para proteger o `roles` | ❌ |
| C | Especifica os atributos que **não** podem ser manipulados | ❌ |
| D | Especifica quais **métodos** da classe podem ser manipulados | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: A.** `setAllowedFields(...)` é uma **allow-list**: lista **os campos permitidos** no bind. Só `nome`, `email`, `senha`, `nomeImagem` podem vir do form; qualquer outro (como `roles`) é **ignorado**.

**Por que as outras estão erradas:**
- **B** — é uma **alternativa** ao DTO, **não** um complemento. Ao adotar o `setAllowedFields`, o curso **reverteu** o bind para a entidade `Usuario` e **removeu** o `usuarioDTO.montaUsuario()`. Os dois resolvem o mesmo problema por caminhos diferentes — não se usam juntos.
- **C** — descreve o **oposto**: especificar o que **não** pode é o `setDisallowedFields` (**blocklist**). `setAllowedFields` é o inverso (allow-list), e mais seguro.
- **D** — atua sobre **campos/atributos** do data binding, **não** sobre métodos. O bind preenche propriedades (via setters), não invoca métodos de negócio.

> 🔑 **Allow-list × blocklist no binder:** `setAllowedFields` = "**só estes** entram" (padrão nega); `setDisallowedFields` = "**estes não** entram" (padrão aceita). Allow-list é mais segura porque um campo sensível **novo** já nasce bloqueado — na blocklist, você teria de lembrar de proibi-lo.

</details>

## 🗂️ Upload inseguro de arquivo → RCE (web shell)

> A Alura Shows guarda a **foto de perfil** no diretório do **Tomcat** e **não valida** o conteúdo/tipo do arquivo. Se em vez de uma imagem eu enviar um **`.jsp` com código Java**, o Tomcat vai **executá-lo** — isso é **RCE (Remote Code Execution)**, a falha mais grave que vimos.

### 💥 Prática — subindo um `.jsp` que roda comando no servidor

1. **No servidor** (onde roda o Tomcat), cria-se um diretório-alvo para provar o efeito:
   ```bash
   cd ~ && mkdir imagemfalsa          # Linux/Mac  (Windows: nova pasta C:\imagemfalsa)
   ```
2. **Na máquina do atacante (Kali)**, escreve-se `imagemfalsa.jsp` — uma JSP que executa um comando do SO:

   **Windows (alvo):**
   ```jsp
   <%@page import="java.lang.*"%>
   <%@page import="java.io.*"%>
   <%
     try {
       Runtime.getRuntime().exec("cmd.exe /c cd C:\\ && rmdir imagemfalsa");
     } catch (IOException e) { e.printStackTrace(); }
   %>
   ```
   **Linux/Mac (alvo):**
   ```jsp
   <%@page import="java.lang.*"%>
   <%@page import="java.io.*"%>
   <%
     try {
       ProcessBuilder builder = new ProcessBuilder(
         "/bin/bash", "-c", "cd [caminho da home] && rm -r imagemfalsa");
       builder.start();
     } catch (IOException e) { e.printStackTrace(); }
   %>
   ```
3. Cadastra-se um usuário (ex.: "Priscila") fazendo **upload do `imagemfalsa.jsp` como foto de perfil**.
4. **Resultado:** o diretório `imagemfalsa` **é apagado** no servidor. O "arquivo de imagem" **rodou como código**. 🚨

> ⚠️ **Apagar uma pasta é só a demonstração.** O mesmo `exec`/`ProcessBuilder` roda **qualquer** comando com os privilégios do Tomcat: abrir um **reverse shell**, baixar malware, ler `/etc/passwd`, criptografar dados (ransomware), pivotar na rede. Um `.jsp` enviado assim é um **web shell** — controle remoto do servidor.

### 🐞 A vulnerabilidade — Unrestricted File Upload

> **Upload irrestrito:** aceitar um arquivo **sem validar tipo/conteúdo** e **guardá-lo num local executável**. Duas falhas somadas fazem o estrago:

| Falha | Detalhe |
|-------|---------|
| **1. Sem validação** | A app aceita qualquer arquivo — não checa extensão, MIME nem "magic bytes". Um `.jsp` passa como se fosse `.png` |
| **2. Local executável** | O arquivo cai **dentro do diretório servido pelo Tomcat**, que **compila e executa** `.jsp`. Bastou acessar a URL do arquivo para o código rodar |
| **Resultado** | **RCE** — o atacante executa comandos arbitrários no servidor. É o topo da escala de gravidade |

> 🔑 **É a mesma doença de novo — "dado tratado como código" — mas no pior lugar:** SQLi (código no **banco**), XSS (código no **navegador da vítima**), e agora **código no próprio servidor**. Por rodar **server-side com os privilégios da aplicação**, o upload inseguro costuma ser **mais grave** que os anteriores.

### ✅ Como se defende (o que corrigir)

| Defesa | Como |
|--------|------|
| **Validar o tipo (allow-list)** | Aceitar **só** extensões/MIME de imagem (`png/jpg/gif`) e conferir os **magic bytes** (assinatura do arquivo), não confiar na extensão/`Content-Type` enviados |
| **Guardar fora da webroot** | Salvar em diretório **não servido** pelo Tomcat (ou num storage/bucket). Se não é servido, não é executado |
| **Local não-executável** | Se tiver de ficar acessível, garantir que o container **não** processe scripts ali (sem mapeamento de JSP/servlet no diretório de uploads) |
| **Renomear + remover extensão** | Gerar nome aleatório e servir via um **controller** (`Content-Disposition`), nunca pelo caminho físico |
| **Limites e varredura** | Tamanho máximo, antivírus/scan, e (defesa em profundidade) rodar o Tomcat com **usuário de baixo privilégio** |

> 💡 **A regra que resolve a raiz:** *arquivo enviado por usuário nunca deve poder ser **executado** pelo servidor.* Valide o que entra **e** guarde onde não roda — as duas coisas. Só validar extensão é burlável (`.jsp;.png`, null byte, case), então **isolar o local** é a barreira mais confiável.

### 📝 Quiz Oficial do Curso — O que o código faz?

> ```java
> Runtime.getRuntime().exec("cmd.exe /c cd C:\\ && rmdir imagemfalsa");
> ```
> O que esse código executa no servidor?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | **Cria** um **diretório** `imagemfalsa` em `C:\` | ❌ |
| B | **Cria** um **arquivo** `imagemfalsa` em `C:\` | ❌ |
| C | **Remove** um **arquivo** `imagemfalsa` em `C:\` | ❌ |
| **D** | **Remove** um **diretório** `imagemfalsa` em `C:\` | ✅ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: D.** O comando `rmdir` (**r**e**m**ove **dir**ectory) do Windows **apaga um diretório**. A linha completa faz: `cmd.exe /c` (executa e encerra) → `cd C:\` (vai à raiz) → `&&` (se deu certo) → `rmdir imagemfalsa` (remove a **pasta**).

**Por que as outras estão erradas:**
- **A** — criar diretório seria **`mkdir`**, não `rmdir`. O `rm`/`rmdir` é a operação **inversa**.
- **B** — criar arquivo seria outro comando (`echo. >`, `type nul >`); `rmdir` não cria nada.
- **C** — a pegadinha: `rmdir` remove **diretório**, **não arquivo**. Apagar um *arquivo* no Windows seria **`del`** (`rm` no Linux). Como o alvo foi criado com `mkdir imagemfalsa` (pasta), o par correto é `rmdir`.

> 🔑 **Além do comando: é RCE.** O que importa para a segurança não é *qual* comando — é que um **arquivo enviado no upload conseguiu executar um comando no servidor**. Trocar `rmdir` por um `powershell -c "..."` de download de malware ou um reverse shell teria o mesmo caminho de entrada. O `rmdir` é só a prova visível do **Remote Code Execution**.

</details>

### 🛡️ A correção do curso — `ImagemValidator` (checar o conteúdo, não a extensão)

> A ideia: antes de salvar, **inspecionar os bytes** do arquivo e só aceitar se forem de uma **imagem de verdade**. O curso usa `URLConnection.guessContentTypeFromStream`, que lê os **primeiros bytes** (os *magic bytes*) e devolve o **MIME** — ou `null` se não reconhecer.

**1. Classe `ImagemValidator`** (pacote `validator`, anotada `@Component`) — recebe o `tratarImagem`/`verifica` com a checagem no início:
```java
@Component
public class ImagemValidator {

    public boolean verifica(MultipartFile imagem, Usuario usuario,
                            HttpServletRequest request) throws IllegalStateException, IOException {

        ByteArrayInputStream bytesImagem = new ByteArrayInputStream(imagem.getBytes());
        String mime = URLConnection.guessContentTypeFromStream(bytesImagem);  // lê os magic bytes
        if (mime == null) {
            return false;          // não reconheceu como imagem → rejeita
        }

        usuario.setNomeImagem(imagem.getOriginalFilename());
        File arquivo = new File(request.getServletContext().getRealPath("/image"),
                                usuario.getNomeImagem());
        imagem.transferTo(arquivo);
        return true;
    }
}
```

**2. Injetar no controller** e decidir no `registrar`:
```java
@Autowired
private ImagemValidator imagemValidator;
...
boolean ehImagem = imagemValidator.verifica(imagem, usuarioRegistro, request);
if (ehImagem) {
    usuarioRegistro.getRoles().add(new Role("ROLE_USER"));   // role fixada no servidor
    dao.salva(usuarioRegistro);
    session.setAttribute("usuario", usuarioRegistro);
    model.addAttribute("usuario", usuarioRegistro);
    return "usuarioLogado";
}
redirect.addFlashAttribute("mensagem", "A imagem passada não é válida!");
return "redirect:/usuario";
```

**Teste:**
| Envio | Resultado |
|-------|-----------|
| O `.jsp` malicioso | **Rejeitado** — `guessContentTypeFromStream` → `null` |
| O mesmo `.jsp` **renomeado para `.jpg`** | **Rejeitado** — a checagem olha o **conteúdo**, não a extensão! |
| Uma imagem **real** | **Aceito** — MIME reconhecido |

> 🔑 **Por que renomear para `.jpg` não engana:** a validação lê os **bytes**, não o nome. Uma JSP renomeada continua começando com `<%@page…` (não com o magic byte de imagem), então o MIME dá `null` e é barrada. **Checar conteúdo > confiar em extensão/`Content-Type`** (que o cliente controla).

### ⚖️ Nota crítica: o *sniff* de MIME é necessário, mas **não** suficiente

O curso melhora muito a situação, mas vale registrar os limites (defesa em profundidade de verdade):

- **`guessContentTypeFromStream` é fraco.** Ele bate contra uma tabela pequena de assinaturas. Um **polyglot** — arquivo que **começa** com magic bytes de imagem válidos (`GIF89a`, `\xFF\xD8\xFF` de JPEG) e **contém código depois** — pode passar como `image/*` **e ainda** carregar payload executável.
- **O arquivo continua salvo em local executável.** O destino é `getServletContext().getRealPath("/image")` — **dentro do webapp**. Se um polyglot passar o *sniff* e for gravado com extensão `.jsp`, o Tomcat ainda o executa. **A checagem de conteúdo não resolve o "onde guardar".**
- **O nome vem do usuário** (`imagem.getOriginalFilename()`) — risco de **path traversal** (`../../`) e de **manter a extensão `.jsp`**. Deveria ser **renomeado** (nome aleatório + extensão derivada do MIME confiável).

> 🔑 **A defesa completa junta as três camadas:** (1) **validar conteúdo** (magic bytes) — *o curso fez*; (2) **guardar fora da webroot / em local não-executável** — falta; (3) **renomear o arquivo** (sem extensão perigosa, sem path do usuário) — falta. O `ImagemValidator` é um ótimo primeiro passo, mas num sistema real ele **sozinho** não fecha o RCE — isolar o local de armazenamento é o que realmente mata o vetor.

> 🧩 **Ciclo do upload completo (neste doc):** **explorar** (web shell `.jsp` → RCE) → **corrigir** (validar o MIME por conteúdo) → **e o que ainda falta** (local não-executável + rename), registrado acima.

### 📝 Quiz Oficial do Curso — O que esse trecho faz?

> ```java
> ByteArrayInputStream bytesImagem = new ByteArrayInputStream(imagem.getBytes());
> String mime = URLConnection.guessContentTypeFromStream(bytesImagem);
> if (mime == null) { return false; }
> ```

| | Alternativa | Veredito |
|--|-------------|----------|
| **A** | Analisa o **conteúdo** do arquivo; se o retorno for **`null`**, retorna `false` e interrompe o cadastro (conteúdo inválido) | ✅ |
| B | Analisa a **extensão** do arquivo (JPG/PNG) e rejeita se for diferente | ❌ |
| C | Pega a **senha** do usuário e tenta descobri-la com `guessContentTypeFromStream` | ❌ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: A.** O código lê os **bytes** do arquivo (`getBytes()` → `ByteArrayInputStream`) e chama `guessContentTypeFromStream`, que inspeciona os **magic bytes** para deduzir o **MIME**. Se não reconhecer (`mime == null`), **não é imagem** → `return false` interrompe o cadastro.

**Por que as outras estão erradas:**
- **B** — a pegadinha central: **não é a extensão**. `guessContentTypeFromStream` olha o **conteúdo** (bytes), não o nome/extensão. É exatamente por isso que renomear o `.jsp` para `.jpg` **não** engana a validação.
- **C** — não faz sentido: `guessContentTypeFromStream` detecta **tipo de arquivo**, não tem qualquer relação com senha. Distrator solto para confundir.

> 🔑 **A distinção que o quiz cobra:** *conteúdo* (magic bytes) × *extensão* (nome). Confiar na extensão é frágil (o usuário controla o nome); ler o conteúdo é mais forte. Ainda assim, lembre da nota crítica acima — nem o *sniff* de conteúdo é infalível (polyglots), por isso **isolar o local de armazenamento** continua essencial.

</details>

### 📝 Quiz Oficial do Curso — Trocar a extensão burla a validação?

> **Afirmação a avaliar:** *"a app ainda falha, pois o usuário pode **trocar a extensão** para uma de imagem e a app aceita."* O que dizer disso?

| | Alternativa | Veredito |
|--|-------------|----------|
| A | **Verdadeira** — `guessContentTypeFromStream` olha a **extensão**; trocá-la anula a validação | ❌ |
| B | **Parcialmente verdadeira** — só funciona se trocar para `.jpg`; para `.png` a validação falha | ❌ |
| **C** | **Falsa** — o método analisa o **conteúdo**; trocar a extensão **não** engana, a checagem continua sobre os bytes | ✅ |

<details>
<summary>Ver gabarito comentado</summary>

**Resposta correta: C.** A afirmação é **falsa**: `guessContentTypeFromStream` inspeciona os **magic bytes**, não o nome. Renomear `imagemfalsa.jsp` → `imagemfalsa.jpg` **não muda os bytes** (continua começando com `<%@page…`), então o MIME dá `null` e o arquivo é rejeitado do mesmo jeito.

**Por que as outras estão erradas:**
- **A** — descreve a validação **por extensão**, que **não** é o que o método faz. Se fosse por extensão, aí sim renomear burlaria — é justamente o erro que o curso corrigiu.
- **B** — não há distinção entre `.jpg` e `.png`: como a checagem é por **conteúdo**, a extensão (qualquer uma) é **irrelevante**. A "parcialidade" é inventada.

> 🔑 **Renomear ≠ burlar (aqui).** Trocar só a extensão não vence uma validação por conteúdo. **Cuidado com o escopo, porém:** a nota crítica acima fala de **polyglot** — que é **mais** que renomear (é *forjar magic bytes* de imagem + embutir payload). Esse é outro ataque, não coberto por esta pergunta; por isso a defesa robusta ainda exige **guardar o arquivo em local não-executável**.

</details>

## 🧠 Conceitos Aprendidos

| Conceito | Definição |
|----------|-----------|
| **XSS** | Injetar JS que executa no **navegador de outros usuários** ([47.md](47.md)) |
| **Stored/Reflected/DOM XSS** | Salvo no BD / refletido da requisição / manipulação no front |
| **Causa** | Entrada **renderizada como HTML** sem escapar (dado tratado como **código**) |
| **Output encoding** | Escapar `< > " &` na exibição — correção principal |
| **CSP** | Header que restringe scripts permitidos |
| **`HttpOnly`** | Cookie inacessível ao JS → limita roubo de sessão via XSS |
| **Spring `Validator`** | Interface (`supports`/`validate`) p/ validar entrada; `rejectValue` marca campo inválido |
| **Blocklist × escape** | Bloquear `<`/`>` é parcial (blocklist); a defesa canônica é **escapar na saída** |
| **`@Valid` + `BindingResult`** | Dispara a validação e captura erros; `BindingResult` vem **logo após** o `@Valid` |
| **`MessageSource` / messages.properties** | Texto das mensagens por código (i18n); `<form:errors>` exibe na JSP |
| **Encoding UTF-8 (mojibake)** | Arquivo **e** `setDefaultEncoding` em UTF-8 — nas duas pontas, senão acentos quebram |
| **Autenticação × Autorização** | *Quem é você?* (login/hash, [90.md](90.md)) × *o que pode fazer?* (ROLES) |
| **ROLES / RBAC** | Papéis (`ROLE_USER`/`ROLE_ADMIN`) controlam **acesso** por parte do sistema → menor privilégio; evita **Broken Access Control** ([89.md](89.md)) |
| **Mass Assignment / over-posting** | Bind de campos sensíveis (`roles`) direto na entidade → **escalonamento de privilégio** (user→admin). Corrige-se com DTO / allow-list de campos / role definida no servidor |
| **DTO (Data Transfer Object)** | Classe só com os campos esperados do form (sem `roles`) → **allow-list por construção**; mapeia p/ a entidade (`montaUsuario`) e desacopla entrada × domínio |
| **`@InitBinder` / `setAllowedFields`** | Allow-list de campos bindáveis no controller (Spring). Alternativa ao DTO; `setDisallowedFields` = blocklist (mais frágil). Mesmo hook que pluga o Validator |
| **Upload inseguro (Unrestricted File Upload)** | Aceitar arquivo sem validar tipo/conteúdo → se cair em local executável (Tomcat), vira **RCE** |
| **Web shell / RCE** | `.jsp` malicioso executado pelo servidor (`Runtime.exec`/`ProcessBuilder`) → comandos arbitrários com o privilégio do Tomcat |
| **Defesa de upload** | Allow-list de tipo + **magic bytes**; guardar **fora da webroot**/local não-executável; renomear; limites/scan; Tomcat com baixo privilégio |
| **Validação por conteúdo (magic bytes)** | `guessContentTypeFromStream` lê os bytes → MIME ou `null`. Ignora extensão (renomear p/ `.jpg` não engana). **Fraco contra polyglot** — não substitui isolar o local |

## ✅ Quiz Mental

1. O que é XSS e qual a **causa-raiz**?
2. Por que este caso é **Stored** e por que isso é o pior tipo?
3. Além do defacement, o que um XSS pode fazer de fato?
4. Qual a **correção principal** e por que "escapar na saída" é melhor que "filtrar na entrada"?
5. Como o `HttpOnly` ajuda **mesmo** havendo um XSS?

<details>
<summary>Ver respostas</summary>

1. XSS é injetar **JavaScript** que roda no **navegador de outros usuários**. A causa-raiz é a app **renderizar a entrada como HTML/JS** em vez de tratá-la como **texto** — o mesmo "dado vira código" do SQLi, agora no HTML
2. É **Stored** porque o payload fica **salvo no banco** (o depoimento) e é servido a **todos** que abrem a página — sem precisar enganar ninguém a clicar. Por atingir **todo visitante automaticamente**, é o mais perigoso
3. Roubar **cookie/sessão** (`document.cookie`) e assumir a conta; **keylog**/phishing; executar **ações como a vítima** (requisições autenticadas); defacement
4. **Output encoding/escaping** — converter `<` `>` `"` em entidades na **exibição**, para o navegador tratar como texto. É melhor que filtrar entrada porque o **contexto de saída** (HTML, atributo, JS, URL) define o que é perigoso; escapar **no ponto de exibição** cobre isso de forma confiável
5. `HttpOnly` impede o **JavaScript** de ler o cookie de sessão (`document.cookie`) — então, mesmo que um XSS execute, ele **não consegue roubar** o cookie de sessão. É defesa em profundidade

</details>
